# CPU 的出路：四条候选路线的判决

*[English](../en/CPU_WAY_OUT.md)*

`CPU_NATIVE.md` 确立了"CPU 原生架构该满足什么"。本文回答它的下一问：
**CPU 上要真正做训练与推理，哪条路走得通、哪条堵死、边界在哪。**

每条路线给机制、实测、判定。数字全部本机实测（i7-8750H / AVX2 / torch 2.14.1+cpu；
GTX 1060 6GB / torch 2.7.1+cu118），每格独立进程，性能实验独占运行。

结论先行（TL;DR）：

| # | 路线 | 判定 | 依据 |
|---|---|---|---|
| 1 | **稀疏 / 条件计算** | **走通，且是 CPU 唯一结构占优区** | B=1 解码 CPU 红利 2.5–3.2×，GPU E8 起反为 0.64–0.91× |
| 2 | 缓存驻留（压工作集进 L2/L3） | **堵死**（训练步不兑现） | 工作集 1–8 MB 全程平坦，无 L3 断崖 |
| 3 | 算子分解 / 小 GEMM | **堵死**（CPU 也不耐分解） | 分解损失 CPU 1.30× vs GPU 1.07× |
| 4 | B=1 长上下文 | **走通**（已证胜过 GPU-Transformer） | 交点 T≈2048，T=8192 快 2.97× |

另有两条**证伪**：`poly_sigmoid` 不比 `torch.sigmoid` 快（见 `CPU_NATIVE.md` §5）；
"CPU 分支 / gather 便宜"不成立（见本文 §3.1）。

---

## 1. 路线一：稀疏 / 条件计算（走通）

### 1.1 现象

同一份负载（d=1024，hidden=4096），稠密 MLP 与 E 专家 MoE（每 token 走 1 个，
有效 FLOPs = 1/E）。CPU / GPU 的**绝对耗时比**：

| 稀疏度 | 2048 token | 8192 token | CPU 稀疏红利 | GPU 稀疏红利 |
|---|---|---|---|---|
| 稠密 | 11.63× | 13.15× | 1.0× | 1.0× |
| E2 | 9.65× | 11.13× | 1.9× | 1.8× |
| E4 | 8.53× | 10.60× | 3.5× | 3.1× |
| E8 | 6.03× | 8.59× | 7.5× | 4.9× |
| E16 | 3.01× | 6.71× | 11.5× | 5.9× |
| E32 | **1.27×** | **3.88×** | **14.5×** | 4.3× |

两个读数：

- **稀疏把 CPU / GPU 的差距从 13.15× 压到 3.88×**；2048 token 下 E32 压到 **1.27×**。
  CPU 与 GPU 的耗时几乎打平。
- CPU 吃到的稀疏红利是 GPU 的 3.4 倍（E32 @ 8192 token：14.5× vs 4.3×）。

### 1.2 机制：不是"分支便宜"，是"小 GEMM 的相对效率"

初始假设是"CPU 有乱序执行与廉价分支，gather 便宜"。**实测证伪**：

| 原语 | CPU | GPU | CPU/GPU 比 |
|---|---|---|---|
| 稠密 GEMM 1024² | 12.63 ms | 1.47 ms | **8.6×** |
| 列 gather | 0.709 ms | 0.039 ms | 18.2× |
| 布尔掩码 | 1.737 ms | 0.456 ms | 3.8× |
| `index_add` | 0.875 ms | 0.123 ms | 7.1× |
| `topk` | 12.73 ms | 3.97 ms | 3.2× |

控制流原语的 CPU/GPU 比（gather 18.2×）**高于**稠密 GEMM（8.6×）——CPU 的 gather 相对**更贵**，
不是更便宜。第二个假设"CPU 更耐算子分解"同样被证伪：

| 拆成 K 个小 GEMM | CPU 损失 | GPU 损失 |
|---|---|---|
| K=1 | 1.000× | 1.000× |
| K=8 | 1.054× | 0.801× |
| K=32 | **1.302×** | **1.074×** |

拆得越细，**CPU 反而损失更大**（1.30× vs 1.07×）。

真正的机制在 **GEMM 效率随行数 M 的曲线**（N=4096、K=1024，即单个专家的权重块）：

| M（路由到该专家的 token 数） | CPU GFLOPS | CPU% 峰值 | GPU GFLOPS | GPU% 峰值 |
|---|---|---|---|---|
| 16 | 77.3 | **31.4%** | 204.2 | **6.8%** |
| 32 | 118.8 | 48.2% | 531.2 | 17.6% |
| 64 | 153.0 | 62.1% | 923.8 | 30.5% |
| 128 | 227.3 | 92.3% | 709.1 | 23.4% |
| 1024 | 225.6 | 91.6% | 1732.6 | 57.3% |
| 4096 | 246.2 | 100% | 3024.2 | 100% |

- CPU 从 M=16 到 4096：77.3 → 246.2 GFLOPS，**3.2×**；
- GPU 同区间：204.2 → 3024.2 GFLOPS，**14.8×**。

**稀疏产生的是"多而小"的 GEMM。CPU 在小 M 下的相对效率是 GPU 的 4.65 倍**
（M=16：31.4% / 6.8%），所以 CPU 兑现更多红利。这不是"分支便宜"，
是 CPU 在没有足够行数填满 SIMD 宽度时**掉得慢**。

### 1.3 落点：稀疏该放哪

稀疏红利在不同场景的兑现程度不同（前向，d=1024）：

| 场景 | token 数 | CPU 红利 E8 | CPU 红利 E16 | GPU 红利 E8 | GPU 红利 E16 |
|---|---|---|---|---|---|
| **B=1 解码** | 1 | **2.53×** | **3.19×** | **0.91×**（变慢） | **0.64×**（变慢） |
| 预填充 1k | 1024 | 4.51× | 5.92× | 4.15× | 2.67× |
| 预填充 8k | 8192 | 6.84× | 9.14× | 5.08× | 6.31× |
| 训练 B8×T256 | 2048 | 5.48× | 7.71× | 3.57× | 2.57× |

**B=1 解码是决定性区**：CPU 有 2.5–3.2× 红利，**GPU 在 E8 起反而变慢**（0.91×、0.64×）。
单序列解码时 GPU 每个专家 kernel 的启动开销无法摊薄，而 CPU 可以。

### 1.4 端到端判决：未穿透（如实记录）

**算子级红利不等于端到端红利**（本仓库第三次同类前例）。真实训练循环
（d=256 / L=4 / T=256 / B=8 / 40 步，同参数量、同 token 流）：

| 结构 | 参数 | ms/token | loss |
|---|---|---|---|
| 稠密 MLP | 4,199,936 | **0.4362** | **5.71** |
| MoE（E=8） | 4,208,128 | 0.4932 | 6.72 |

端到端 **0.884×（更慢 13%）**，且质量更差。原因是逐专家循环的索引与
`index_add` 开销在反向被放大。

⇒ **判定**：稀疏路线**走通，但落点是纯前向路径**（B=1 解码、预填充），
不是训练反向。要进训练，须先把路由开销从 eager 循环里消掉（融合分组 GEMM /
自定义 kernel），否则端到端不兑现。

## 2. 路线二：缓存驻留（堵死）

`CPU_NATIVE.md` §3 测出单线程流式带宽在 3–4 MB 处断崖（26.7 → 15.4 GB/s），
据此推测"把工作集压进缓存"是杠杆。**训练步上不兑现**：

| 配置 | 激活估计 | ms/token |
|---|---|---|
| B8 × T64 | 0.98 MB | 0.1223 |
| B8 × T128 | 1.97 MB | 0.2202 |
| B8 × T256 | 3.93 MB | 0.1298 |
| B8 × T512 | 7.86 MB | 0.1318 |
| B4 × T512 | 3.93 MB | 0.1229 |
| B2 × T1024 | 3.93 MB | 0.1206 |

工作集从 0.98 MB 涨到 7.86 MB（跨越断崖点），ms/token **全程平坦在 0.12–0.13**，
**无断崖**。T=128 的 0.22 是 chunk 对齐的调度假象，不是缓存效应。

⇒ **判定**：训练步的瓶颈是**每 token 的算子调度**（与 `CPU_HEADROOM.md` §一 一致：
4524 次 aten/步、反向占 56.9%），不是缓存驻留。缓存论只对**单线程流式访存**
成立，对真实训练步无预测力。

---

## 3. 路线三：算子分解（堵死）

见 §1.2 的分解实验：CPU 拆到 K=32 损失 1.30×，GPU 只损失 1.07×。
**CPU 不耐受小算子分解**——这与"CPU 适合多而小的任务"的直觉相反。
（这条也解释了为什么融合内核在 CPU 上有收益：§22 实测训练步 1.10–1.17×。）

---

## 4. 路线四：B=1 长上下文（走通）

`CPU_NATIVE.md` §4 已给出 B=1/T=2048 时 CPU-SunnyNet 快过 GPU-Transformer 1.15×。
本文把前沿补全（同栈参数 d=256/L=4，两边都用单步 + KV cache 路径）：

| T | SunnyNet 单步 | Transformer 单步 | Transformer/SunnyNet |
|---|---|---|---|
| 128 | 5.10 ms | 3.09 ms | 0.606× |
| 512 | 4.68 ms | 3.67 ms | 0.784× |
| **2048** | 4.96 ms | 5.06 ms | **1.021×（交点）** |
| 4096 | 6.59 ms | 13.01 ms | 1.976× |
| 8192 | 7.11 ms | 21.13 ms | **2.971×** |

- SunnyNet 单步基本平坦（O(1)，4.6–7.1 ms）；
- Transformer 随 T 线性上升（O(t)，3.1 → 21.1 ms）；
- **交点 T ≈ 2048**，此后递推架构稳定领先，T=8192 时快 2.97×。

⇒ **判定**：走通。这是唯一已证"CPU 胜 GPU"的区间，应作为 CPU 原生模型的主目标场景。

## 5. 质量问题的根因：状态坍缩与召回容量

外部 Kaggle 运行的输出被指"不连贯"。核实后区分出两个独立原因。

### 5.1 外部运行的账（CodeDoes/SunnyNet-P100M-Kaggle）

- 102,126,662 参数，24,000 步 × B8 × T512 = **98.3M token**，val loss 2.4759 / **ppl 11.89**；
- 跑在 **Kaggle P100（GPU）**，不是 CPU；
- 预算比：98.3M / 102M = **0.96 token/参数**，Chinchilla 建议 20 ⇒ **缺口 20.8×**；
- 只跑 `en_literature` 单域，该域训练集仅 **4.34M token** ⇒ 数据被反复咀嚼约 **22 遍**。

### 5.2 "不连贯"是状态坍缩，不是随机失误

40 条样本里，多个互不相关的输入产出同一段文本：

| 输入 | 输出片段 |
|---|---|
| `Once upon a time,` | and was horning to the days ... |
| `The old house stood` | ne with the carching of the **scape of the visic of the place, of the eyes** |
| `At the edge of the sea,` | ... **scape of the visic of the place, of the eyes** |
| `The captain turned and` | suref a smoke of the **scape of the visic of the place, of the eyes** |

8 条抽样里 `"scape of the"` 出现 5 次、`"visic of the place"` 4 次。
**不同输入收敛到同一轨迹 = 吸引子坍缩**，不是逐 token 的采样噪声。

### 5.3 本机复现：坍缩随层数累积

`experiments/_state_collapse.py`（small 预设、zh_ancient 400 步）测逐层状态的
不同输入成对余弦相似度：

| 层 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| 成对相似度 | 0.308 | 0.212 | 0.338 | **0.526** |

从第 1 层到第 4 层，不同输入的状态越来越像。随机初始化基线仅 **0.0043**，
排除"测量噪声"解释。**层数越深坍缩越重**——14 层的 p100m 比 4 层严重得多，
与外部观察一致。

### 5.4 架构级上限：精确召回容量

`experiments/_recall_capacity.py`：序列 `k1 v1 ... kn vn kq`，预测 `v_q`
（键值词表 64，d=64，800 步）：

| 对数 n | 递推 acc | 注意力 acc |
|---|---|---|
| 2 | **0.0469** | **0.9336** |
| 4 | 0.1211 | 0.6094 |
| 8 | 0.1133 | 0.2578 |
| 16 | 0.0430 | 0.0742 |

递推在 2 对时仅 **4.7%**（随机 1/64 = 1.6%），注意力 **93.4%**。
SunnyNet 的状态是**逐通道标量**（small 每层 128 个数，`init_state` 形状 `(1,4,128)`），
容量天然有限。对照：DeltaNet / RWKV-7 用**逐 head 矩阵值状态**，容量高一个量级。

⇒ **判定**：不连贯有两个独立来源——(a) 训练预算不足（缺口 20.8×）；
(b) **元素级状态的召回容量上限**。前者靠加数据解决，后者必须改状态形态。

## 6. 结论：CPU 出路的形态

把四条路线的判决合起来，CPU 原生模型的设计目标收敛为：

**`O(N)` 递推骨架 + 稀疏前向 + 元素级状态升级 + 面向 B=1 长上下文**

| 设计项 | 依据 | 状态 |
|---|---|---|
| O(N) 递推（无 token 两两交互） | §4 交点 T≈2048 | 已满足（SunnyNet） |
| 长上下文单序列为主目标 | §4 T=8192 快 2.97× | 待收紧目标 |
| 前向稀疏（MoE / top-k） | §1.3 B=1 解码 CPU 2.5–3.2×，GPU 反慢 | 待实现 |
| 训练反向**不用**稀疏 | §1.4 端到端 0.884× | 纪律 |
| **状态从元素级升到矩阵值** | §5.4 召回 4.7% vs 93.4% | **待改架构** |
| 层内加"抗坍缩"机制 | §5.3 相似度随层升到 0.53 | **待改架构** |

最紧要的两条（P0）：

1. **状态形态**：元素级 → 矩阵值（每 head 一个 d×d 子矩阵）。DeltaNet 已验证可行，
   CPU 上代价是状态读写从 `dim` 增到 `n_head × d_head²`，但换来召回容量提升。
2. **抗坍缩**：在层内引入一个不随深度累积的输入通路（如跨层直接注入、
   或对状态反馈项做归一化约束）。§5.3 的逐层相似度是免费的诊断指标，可直接接进测试。

```sh
# 稀疏亲和性（CPU / GPU 各跑一次）

# 稀疏红利随规模
python -X utf8 experiments/_sparse_dividend.py --device cpu

# 机制归因：控制流原语 / 分解容忍 / GEMM M 曲线
python -X utf8 experiments/_route_mechanism.py --device cpu
python -X utf8 experiments/_decomp_tolerance.py --device cpu
python -X utf8 experiments/_gemm_m_curve.py --device cpu

# 落点：稀疏在哪个场景兑现
python -X utf8 experiments/_sparse_where.py --device cpu

# 端到端判决
python -X utf8 experiments/_sparse_e2e.py --device cpu --steps 40

# 缓存曲线
python -X utf8 experiments/_cache_curve.py --preset smalln80

# 解码前沿
python -X utf8 experiments/_decode_frontier.py --device cpu

# 质量根因
python -X utf8 experiments/_recall_capacity.py
python -X utf8 experiments/_state_collapse.py --preset small --steps 400
```

边界：全部结论限于本机（AVX2-only 的 2018 年移动 CPU）。
有 AVX-512 / VNNI / AMX 的机器上，小 M GEMM 效率与稀疏红利都需重测。
