# CPU 原生模型设计准则

*[English](../en/CPU_NATIVE.md)*

本文回答一个问题：**主流架构是否为 GPU 而生？CPU 原生架构应该长什么样？**

结论先行：是，且可量化。但"为 GPU 而生"的原因不是通常认为的"算力差"。

全部数字本机实测（i7-8750H / AVX2 / torch 2.14.1+cpu；GTX 1060 6GB / torch 2.7.1+cu118），
脚本见 `experiments/_machine_balance.py`、`_cpu_gpu_crossover.py`、`_cache_cliff.py`、
`_device_affinity.py`、`_transcendental_cost.py`。

---

## 1. 机器平衡：两设备几乎相同（证伪一个常见说法）

"CPU 访存受限、GPU 算力受限"是常见叙事。实测不支持：

| 设备 | fp32 GEMM | 拷贝带宽 | 机器平衡 |
|---|---|---|---|
| i7-8750H（6C12T, AVX2） | 216.1 GFLOPS | 11.5 GB/s | **18.7 FLOP/字节** |
| GTX 1060 6GB | 2878.2 GFLOPS | 153.1 GB/s | **18.8 FLOP/字节** |

两者的 FLOP/字节**几乎相同**。GPU 的算力高 13×，带宽也高 13×，代数和相抵。
⇒ **瓶颈不在"哪一类资源"，而在"问题规模能否填满该资源"。**

---

## 2. 真正的分歧：问题规模

GEMM 尺寸扫描（GFLOPS）：

| n | CPU | GPU |
|---|---|---|
| 64 | **23.5** | 9.0 |
| 128 | **215.2** | 74.9 |
| 256 | 227.6 | **573.5** |
| 1024 | 258.7 | **1168.1** |
| 4096 | 322.3 | **3032.3** |

**n ≤ 128 时 CPU 赢**（n=128：215 vs 75，2.9×）。

B=1 单序列 GEMV（解码态负载，µs/token）：

| dim | CPU | GPU |
|---|---|---|
| 256 | **19.1** | 47.7 |
| 512 | **18.6** | 47.7 |
| 1024 | 42.6 | **42.4** |
| 2048 | 598.4 | **109.9** |
| 4096 | 2746.5 | **421.9** |

两个事实：
1. **GPU 有约 47 µs 的启动地板**（dim 256 与 512 同值），与小尺寸无关；
2. **dim ≤ 512 的 B=1 解码，CPU 快约 2.5×**。

GPU 的强项是把大矩阵并行铺满；一旦每步工作量小于启动开销，它就输。

## 3. 缓存断崖

L2 = 1536 KB、L3 = 9216 KB（i7-8750H）。单线程流式有效带宽随工作集：

| 工作集 | 有效带宽 |
|---|---|
| 256 KB | 18.8 GB/s |
| 512 KB | 24.6 GB/s |
| 2048 KB | 26.7 GB/s |
| 4096 KB | 15.4 GB/s ← 断崖 |
| 262144 KB | 11.0 GB/s |

**工作集超过约 3–4 MB 即离开高带宽区。** 这是 CPU 侧唯一的"本地资源"——
L3 里的数据访问代价远低于 DRAM。

---

## 4. 设备亲和性：主流架构确实更"GPU 原生"

同参数量对齐（栈参数约 366K）、同批输入、前向 ms/token。
**GPU 倍数 = CPU 耗时 ÷ GPU 耗时**，越大说明该架构从 GPU 获益越多：

| 架构 | B,T | CPU | GPU | GPU 倍数 |
|---|---|---|---|---|
| sunnynet | 1,256 | 0.0545 | 0.0484 | 1.13× |
| sunnynet | 1,2048 | 0.0279 | 0.0095 | 2.94× |
| sunnynet | 8,256 | 0.0366 | 0.0060 | 6.10× |
| sunnynet | 8,1024 | 0.0426 | 0.0030 | 14.20× |
| transformer | 1,256 | 0.0685 | 0.0240 | 2.85× |
| transformer | 1,2048 | 0.3344 | 0.0322 | **10.39×** |
| transformer | 8,256 | 0.0521 | 0.0057 | 9.14× |
| transformer | 8,1024 | 0.2000 | 0.0169 | 11.83× |

关键读数：

- **长上下文单序列**（B=1,T=2048）：Transformer 的 GPU 倍数是 **10.39×**，
  SunnyNet 只有 **2.94×**。差距来自 O(T²) 注意力的并行形状——GPU 极擅长，
  CPU 极不擅长。**这就是"为 GPU 而生"的可测形态。**
- **真实交叉**：B=1/T=2048 时 **CPU 上的 SunnyNet（0.0279）快于 GPU 上的 Transformer
  （0.0322）1.15×**。这是"16G 内存追平 8G 显卡"唯一被实测支持的场景。
- 训练步（60 步实测）：CPU 上 sunnynet 0.129 vs transformer 0.173 ms/tok（SN 快 1.34×）；
  切到 GPU 后 0.024 vs 0.021（Transformer 反快 1.14×）。
  **CPU 优势在切到 GPU 时消失**——这正是"亲和性"的定义。

## 5. 被证伪的前提

常见论证："CPU 无硬件 sigmoid，架构应改用有理式逼近以省超越函数"。
本机实测不支持：

| 宽度 | torch.sigmoid | poly_sigmoid | 倍数 |
|---|---|---|---|
| 256 | 0.224 ms | 0.375 ms | 0.60× |
| 640 | 0.594 ms | 4.426 ms | 0.13× |
| 2048 | 2.677 ms | 17.369 ms | 0.15× |

`poly_sigmoid`（仅加/绝对值/除法）**比 torch.sigmoid 慢 1.7–7.7×**：
AVX2 确实没有硬件 sigmoid，但 torch 的向量化实现已足够好，
而 `abs` + 逐元素除法在本机并不便宜。

⇒ **不得以"超越函数在 CPU 上贵"为由设计激活函数。** 该前提在本机为假。

（此结论限于本机 AVX2；有 AVX-512 或硬件高精度倒数的机器需重测。）

## 6. 由此得到的 CPU 原生设计准则

每条都可检验，附检验方式。

| 准则 | 依据 | 检验 |
|---|---|---|
| **工作集压进 L2/L3（≤ 3 MB）** | §3 断崖 | 逐层激活+权重驻留量实测 |
| **矩阵维度贴近 n ≤ 128 的 CPU 甜点区** | §2 | GEMM 尺寸扫描 |
| **单步延迟必须压到 47 µs 以下才有意义** | §2 GPU 启动地板 | B=1 单步计时 |
| **目标场景是 B=1、长上下文、小维度** | §4 真实交叉 | 与 GPU 上的对照架构同场比 |
| **不靠超越函数省钱** | §5 证伪 | 激活函数微基准 |
| **减少算子数量优先于加宽矩阵** | CPU_HEADROOM §1（4524 次 aten/步） | 训练步剖析 |

## 7. SunnyNet 现状对照

| 准则 | SunnyNet | 判定 |
|---|---|---|
| O(N)、无 token 两两交互 | 滚动状态 + 一阶递推 | 已满足 |
| 规避巨型稠密矩阵 | 低秩分解 + 深度可分卷积 + 三对角滤波 | 已满足 |
| 状态有界 | 凸组合，`\|s_t\| ≤ max(\|s_0\|,\|u_t\|)` | 已满足 |
| 不保存整条激活 | 可逆重算 | 已满足 |
| 工作集 ≤ 3 MB | 未测 | **待核** |
| 维度落在 n ≤ 128 甜点区 | `proto20mw` d640 偏大 | **待核** |
| 单步 < 47 µs | 1.4M ckpt 单步 2.49–2.19 ms | **未达**（B=1 小模型） |

SunnyNet 已满足大部分结构准则，但**第 6–7 条（规模落点）未验证**。
过往优化集中在"减算子"，没有按"缓存驻留"和"维度甜点"系统性标定过。

## 9. 两项后续实测

### 9.1 工作集驻留（`experiments/_working_set.py`）

即便最小预设，**计入激活后也超出缓存高效区**：

| 预设 | 矩阵权重 | 单层激活+分摊权重 | 判定 |
|---|---|---|---|
| small (d128/L4) | 1.38 MB | 10.35 MB | 超高效区 |
| smalln80 (d80/L4) | 1.39 MB | 7.85 MB | 超高效区 |
| proto20mw (d640/L6) | 63.81 MB | 68.99 MB | 溢出 L3 |

矩阵权重本身（1.38 MB）**能进 L2**，但 `B=8/T=256` 下**单层激活（6.9–9 MB）就撑爆 L3**。
⇒ 当前配置的瓶颈是**激活工作集**，不是权重。减小 B/T 或分块重算才是对齐 §6 准则的杠杆。

### 9.2 维度甜点（`experiments/_dim_sweetspot.py`，300 步 / T=256 / B=8）

| dim | L | 栈参数 | ms/token | ppl |
|---|---|---|---|---|
| 64 | 4 | 756,628 | **0.0856** | 96.94 |
| 96 | 4 | 1,150,292 | 0.1057 | 86.50 |
| 128 | 4 | 1,677,076 | 0.1410 | 82.17 |
| 192 | 4 | 2,908,820 | 0.2315 | **78.10** |

耗时随 d **单调上升**，ppl 随 d **单调下降**——**没有非单调的甜点**。

⇒ **证伪**"存在一个 CPU 特有的最优维度"。§2 的 n≤128 GEMM 甜点区只说明**单个矩阵**
在该尺寸高效，但不代表整个模型应在该维度——参数预算才是主导（d 越大参数越多，
质量越好也越慢）。维度是纯权衡，不是可优化的极值点。
