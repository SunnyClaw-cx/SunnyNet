核心结论：融合 + 减层加宽让同架构更快也更好；窄残差流 + `p.clamp` 判掉后训练速度追平 rwkv（统计持平），对 h3/mamba/hyena/linear 稳定领先。

- **质量**：§12 修正后 T=256 ppl 七架构**第二**（57.83，仅次于 H3 53.93）；
  20M 规模减层加宽后 ppl **再降 10.9%**（54.82 vs 61.55，400 步未收敛），
  并在 20M 同协议对照中**升至五架构第一**（§14.6）。
- **前向速度**：对 Transformer T≳384 后更快（T=4096 快 22.69×，已复核）；
  对同样 O(N) 的同行**没有稳定的领先区间**——随 T 从第 6 名追到第 3 名（§10.6），
  全程未登顶（hyena 始终第一）。
- **训练态内存**：T=1024 下峰值 RSS **1812 MB**，在七架构中**第 2 低档**，
  比 Transformer（3192 MB）省 **43%**，与 O(N) 同行同档（§17）。
- **训练速度**：算子融合在**同架构上**提速 19–41%；减层加宽**再快 12–17%**；
  **窄残差流（dim 128→80）+ `p.clamp` 判掉（§16）**在等栈参数下**再快 17.7–20.7%**——
  由此训练步 T=256 名次**升至第一**（0.0953 ms/tok，名义快 rwkv 3.0%），
  T=512 与 rwkv 相差 3.7%，逐轮配对检验不显著 ⇒ 按纪律记为"与 rwkv 统计持平"；
  对 h3/mamba/hyena/linear_attn 稳定领先 16–41%。rwkv 仅名义领先，**"超越"未达成**。
  融合 kernel 的收益上界实测仅 8.8%（§14.7），优先级低于已落地的改动。
- **持平的边界**：仅 `L=4` 下成立；层数对齐到 `L=6` 时同预算窄配置反慢 30–40%（§16.5）。
  机制见 §28：每层一笔固定算子派发税，同预算下"浅而宽"在速度与质量两条轴上都更优。
  且 T≥1024 同行优势仍在（§13 结论在旧配置下依然成立）。
- **规模化**：20M 与 100M 可运行并已对照；**0.5B 在 CPU fp32 不可实例化，GPU 上仅前向与
  最朴素 SGD 可跑（AdamW/动量 SGD 均 OOM），且多步 loss 无下降 → 无 0.5B 质量结论**。
- **GPU 侧的定位**：本机 GPU 用于**正确性验证与加速比测量**（前向 8.0–15.2×、训练步
  9.9–12.5×，未做 CUDA 侧优化，是下界）。**不用于内核级优化**——无 nvcc / 无 CUDA
  toolkit / 无 triton，且 GPU 上扫描与门控占比不足 5%，融合收益空间比 CPU 更小（§15.5）。
- **scaling 趋势并非单调**：20M 时质量第一（§14.6），但 **100M 时退回第二**（§14.8，
  落后 rwkv 3.6%）。现有证据只支持"20M 附近质量有竞争力、100M 与 rwkv 同档"，
  不支持"规模越大优势越大"。

适用性取决于目标任务的序列长度与"质量优先还是速度优先"的取舍。

## 2. 核心实验：O(N) 优势的实测验证

这是本架构唯一的主张，只能靠数据检验。方法：固定模型（`small`），  
改变输入序列长度，测量单次前向耗时。

![序列缩放](../figures/seq_scaling.png)

### 2.1 数据

| 序列长度 T | SunnyNet | Transformer | 耗时比 (TF/Sunny) |
| ------ | -------- | ----------- | -------------- |
| 256    | 45.6 ms  | 17.5 ms     | 0.38×          |
| 512    | 80.3 ms  | 62.5 ms     | 0.78×          |
| 1024   | 147.7 ms | 167.0 ms    | **1.13×**      |
| 2048   | 215.8 ms | 542.1 ms    | **2.51×**      |
| 4096   | 319.9 ms | 4041.8 ms   | **12.63×**     |

### 2.2 结论

1. **O(N) 主张成立**：SunnyNet 耗时随 T 近似线性（45.6→319.9ms，T 增 16 倍，耗时增 7 倍，  
   斜率随 T 增大反而变缓——固定开销被摊薄）。Transformer 呈 O(T²) 爆炸（17.5→4041.8ms，T 增 16 倍，耗时增 230 倍）。
2. **交叉点 T≈834**：序列短于此，SunnyNet 更慢；长于此，SunnyNet 更快。
3. **短序列劣势的来源**：T=256 时 Transformer 仅 17.5ms，SunnyNet 45.6ms。  
   原因是 SunnyNet 逐 token 的滚动状态计算包含多次元素级操作（竞争门控、扫描、循环滤波），  
   常数因子高于一次稠密 matmul。序列短时，Transformer 的并行 matmul 效率占优。

> **这一结果是关键的**：任何"SunnyNet 全面更快"的说法都与此数据矛盾。  
> 准确表述是：SunnyNet 用短序列的常数因子劣势，换取长序列的线性复杂度优势。

### 2.3 交叉点依赖 batch 大小

§2.1 的延迟测量为 **batch=1、仅前向**。在 **batch=8 的训练**中（§3），T=256 时 SunnyNet 反而  
快 8.4%（0.2831 vs 0.3089 ms/tok）——**与 batch=1 前向的结论相反**。

| 测量条件              | T=256 时谁更快                        |
| ----------------- | --------------------------------- |
| 前向，batch=1        | Transformer（17.5 vs 45.6 ms）      |
| 训练（前向+反向），batch=8 | SunnyNet（0.2831 vs 0.3089 ms/tok） |

**原因**：batch=1 时矩阵极小，SunnyNet 的多个元素级算子受 **PyTorch 逐算子调度开销**主导；  
batch 增大后 matmul 效率提升，同时 Transformer 的注意力计算量随 batch 线性放大，  
使交叉点**向更小的 T 移动**。

→ **结论修正**：交叉点 **T≈834 仅是 batch=1 前向的值**，不是普适常数。  
它随 batch、是否含反向、线程数而变。决策时应按目标任务的真实 batch/长度组合实测，  
不能直接套用单一数字。

### 2.4 测量纪律修正（进程隔离后重测，数值与原 §2.1 不一致）

**发现**：§2.1 的绝对耗时不可复现。同一模型在同一进程"构建过多个模型之后"测量，
耗时可达干净进程的 **2 倍以上**（实测 T=4096：325 ms vs 776–822 ms）。
原因是堆碎片与分配器状态随同进程内累积的模型构建而劣化，且**对不同架构的放大倍数不同**。
这使 §2.1 及早期版本的架构间耗时比全部失真。

**修正做法**：每个 `(架构, 序列长度)` 单元格单独起一个子进程，进程内只构建一个模型。
脚本 `experiments/on_scaling.py`。重测结果（batch=1、前向、8 线程、重复 9 次取中位数）：

| 序列长度 T | SunnyNet | Transformer | 耗时比 (TF/Sunny) | IQR |
|---|---|---|---|---|
| 128  | 14.0 ms | 7.5 ms | 0.53× | 19% / 26% |
| 256  | 19.5 ms | 13.5 ms | 0.69× | 3.5% / 15% |
| 512  | 26.4 ms | 40.8 ms | **1.55×** | 12% / 6% |
| 768  | 34.6 ms | 87.3 ms | **2.53×** | 9% / 3% |
| 1024 | 50.0 ms | 141.2 ms | **2.83×** | 6% / 7% |
| 1536 | 58.0 ms | 315.4 ms | **5.44×** | 13% / 4% |
| 2048 | 98.1 ms | 638.2 ms | **6.51×** | 7% / 6% |
| 4096 | 148.7 ms | 3373.4 ms | **22.69×** | 4% / 3% |

**与 §2.1 的差异与解释**：

| 项目 | §2.1（污染） | §2.4（进程隔离） | 说明 |
|---|---|---|---|
| T=256 耗时比 | 0.38× | 0.69× | 污染对 SunnyNet 放大更多 |
| 交叉点 | T≈834 | **T≈384**（6 层 TF）/ **T≈600**（4 层 TF） | 交叉点随对照模型深度移动 |
| T=4096 耗时比 | 12.63× | **22.69×** | 污染压缩了真实差距 |

**保留原值的理由**：§2.1 与 §2.3 的**方向性结论仍成立**（短序列慢、长序列快、
交叉点随 batch/深度移动），但其**绝对数值与 12.63× 应视为下界**。
README 的"12.6 倍"与本表的"22.7 倍"均以进程隔离口径为准时，后者更接近真值；
但两者都只在各自测得的条件下成立，**脱离条件即不可引用**。

**22.69× 的复核（2026-10-20，融合改动后重测）**：

| 项 | 值 |
|---|---|
| 原始数据 | `experiments/results/seq_scaling.json`：T=4096 时 148.66 ms vs 3373.42 ms = **22.69×**，IQR 3.94% / 2.69% |
| 复核数据 | `experiments/results/verify_22x.json`：131.9 ms vs 3709.9 ms = **28.12×**（当前融合后代码），IQR 10.6% / 14.6% |
| 条件（须随数字一起引用） | **batch=1、纯前向（不含反向）、8 线程、1.4M 小模型** |

⇒ **该数字真实可复现**，融合改动后比值不降反升（22.69 → 28.12，因融合对 SunnyNet 的
前向加速大于对 Transformer 的）。但它是前向延迟比，不是训练速度比 ——
batch=8 训练步对 O(N) 同行仍落后（§13）。

**另一处口径说明**：§2.4 的 `22.69×` 与 §10.6 的"前向对同行只在 512<T<2048 领先"
**并不矛盾**。前者对标量注意力的 Transformer（O(T²)，T=4096 时差距按 T² 放大），
后者对标同为 O(N) 的线性类架构（差距由常数因子决定，T 越大越不利于 SunnyNet）。

## 3. 质量对照：能否持平？

速度不是唯一指标。同 token 预算（1200 步 × batch 8 × T 256 ≈ 245 万 token）下比较质量。

![基线对照](../figures/speed_compare.png)

![训练曲线](../figures/loss_curves.png)

| 指标                 | SunnyNet      | Transformer | 差距              |
| ------------------ | ------------- | ----------- | --------------- |
| 验证损失               | 4.3367        | **4.2895**  | +1.10%          |
| 验证困惑度              | 76.46         | **72.93**   | +4.84%          |
| 每 token 耗时 (T=256) | **0.2831 ms** | 0.3089 ms   | SunnyNet 快 8.4% |
| 峰值内存               | 896 MB        | 879 MB      | +1.9%           |
| 平均梯度范数             | 0.8445        | 0.4838      | —               |

**读数**：

- 在小规模、短序列设置下，质量接近但**略逊**：val loss 高 1.10%、ppl 高 4.84%。
- **但这 4.84% 的差距不能判定 Transformer 更优**：同配置下种子噪声的 ppl 极差为 6.32（§6），  
  **大于**两架构间的 3.53。基线对照只跑了单种子，差异落在噪声量级内。  
  严格结论是：两者在小规模短序列下统计上不可区分，需要多种子对照才能定论（见 §8 待改进项）。

  方向一致但幅度以 §13 为准；**对 mamba/h3/hyena 则全长度落后**。

> **口径更正**：§3 的"每 token 耗时 0.2831 ms"与 §13 的 0.1858 ms 不可比——
> 前者为未隔离测量（同进程已构建多个模型），后者为独立子进程。
> **同一配置下未隔离测量使读数偏高约 50%**，这与 §2.4 记录的 2 倍级放大同源。

## 4. 20M 规模对照

### 4.1 单步训练开销（实测，batch 4，T=512）

| 架构          | 单步耗时        | 每 token 耗时   | 总参数        |
| ----------- | ----------- | ------------ | ---------- |
| SunnyNet    | 3.755 s     | 1.834 ms     | 20,955,698 |
| Transformer | **2.200 s** | **1.074 ms** | 22,086,960 |

> **警告**：20M、T=512 下 SunnyNet **单步反而慢 71%**（1.834 vs 1.074 ms/tok）。  
> 原因有二：(a) T=512 仍**低于交叉点 834**；(b) 20M 规模下 SunnyNet 的逐 token 元素级算子  
> （低秩投影后仍有 d→inner 的稠密乘法）常数因子劣势被放大。
>
> 这意味着：SunnyNet 的适用区间由序列长度决定，而非模型规模。  
> 放大模型并不能让它在短序列上反超。

### 4.2 20M 训练质量对照（300 步）

> **说明**：300 步对 20M 模型远未收敛（val 仍在快速下降：5.73→5.55→5.49），  
> 此处数值仅用于确认"训练可正常进行、梯度不爆炸、内存不失控"，  
> **不作为质量对照结论**。

| 架构          | 总参数        | 栈参数        | val loss   | ppl        | ms/token  | 峰值内存    | 平均梯度范数 | wall   |
| ----------- | ---------- | ---------- | ---------- | ---------- | --------- | ------- | ------ | ------ |
| SunnyNet    | 20,955,698 | 16,761,394 | 5.4883     | 241.84     | 3.1642    | 2579 MB | 1.846  | 1987 s |
| Transformer | 22,086,960 | 16,762,160 | **5.0955** | **163.29** | **2.281** | 1689 MB | 0.779  | 1430 s |

**SunnyNet 在 20M、T=512 下质量与速度双输**：ppl 高 **48.1%**（241.84 vs 163.29），  
每 token 慢 **38.7%**（3.164 vs 2.281 ms），内存高 **52.7%**（2579 vs 1689 MB）。  
这是明确不利的结果。

**原因分析**：

1. T=512 **低于交叉点 834**，SunnyNet 的 O(N) 优势尚未展开，常数因子劣势完全暴露。
2. SunnyNet 的逐 token 算子链较长（归一化 → 卷积 → 低秩投影 → 竞争门控 → 扫描 → 输出反馈），  
   在 20M 维度下每个算子的调度与访存开销被放大；Transformer 则是少数几次大矩阵乘。
3. 内存更高（2579MB）源于扫描需保存整段状态 `(B,T,d)`，而 Transformer 的激活由  
   PyTorch 逐层释放。

**结论**：SunnyNet 是长序列专用方案，不是更省资源的通用替代品。  
在短序列上放大模型规模只会放大它的劣势。

**训练健康度读数**（SunnyNet）：

- 梯度范数 0.84–1.93 波动，**未爆炸也未消失**，10 层深度可接受。
- 峰值内存 2579 MB，**无换页风险**（本机 15.87 GB）。
- val loss 单调下降（5.7325 → 5.5545 → 5.4883），训练稳定。

**测量污染提示**：SunnyNet 的 ms/token 三次记录为 2.527 → 2.477 → **3.164**，  
末段明显升高，系**测量期间 CPU 竞争加剧**所致，非模型变慢。

## 5. 消融实验

![消融](../figures/ablation.png)

600 步，`small` 预设，逐组件关闭：

| 变体            | val loss   | ppl       | ms/token |
| ------------- | ---------- | --------- | -------- |
| full（完整）      | 4.5681     | 96.36     | 0.4528   |
| no_decay_gate | **4.5539** | **95.01** | 0.3231   |

| none（全关）      | 4.6058     | 100.06    | 0.2063   |

**消融实验的三个问题**：

- 关闭单个组件后 ppl **反而更低**（如 no_current 94.92 < full 96.36），  
  这在原理上不可能出现在充分训练的模型上。
- 原因是 **600 步远未收敛**（参见训练曲线，1200 步时 loss 仍在下降）。  
  未收敛时，模型容量越小反而"过拟合得更慢"，ppl 读数受噪声主导。
- 因此本消融实验不构成任何组件有效性的证据，只说明"全关（none）确实最差"（100.06），  
  即这些组件**确实在贡献计算**（虽然方向未定）。
- 消融应在充分收敛的 checkpoint 上、或至少数倍于当前步数下进行。  
  这是**待改进项**，不是可用结论。

## 6. 种子稳定性

600 步，3 个随机种子：

| 种子             | val loss            | ppl          |
| -------------- | ------------------- | ------------ |
| 1234           | 4.5681              | 96.36        |

质量差异**应判定为"统计上不可区分"**，而非 Transformer 更优。

## 7. 长序列训练对照（交叉点的直接验证）

§2 的交叉点结论由**前向延迟**得出。为验证它在**真实训练**中同样成立，  
在 T=1024（**高于交叉点 834**）上做训练对照（200 步，batch 4，`small` 预设）。

![长序列训练对照](../figures/longseq_train.png)

| 指标         | SunnyNet      | Transformer | SunnyNet 优势 |
| ---------- | ------------- | ----------- | ----------- |
| 每 token 耗时 | **0.2623 ms** | 0.5445 ms   | **快 2.08×** |
| 验证损失       | **5.1320**    | 5.3702      | 优 4.4%      |
| 验证困惑度      | **169.35**    | 214.92      | **优 21.2%** |

| 栈参数        | 365,332       | 361,952     | 对齐（差 0.9%）  |

**这是最重要的正面结果**：在 T=1024 下，SunnyNet **同时**在速度、质量、内存  
三个维度全面优于同参数量 Transformer。三项优势**方向一致、幅度可观**，  
不是噪声（ppl 优势 21.2% 远大于种子噪声 ~6%）。

**结论自洽：适用性完全由序列长度决定，分界在 T≈834 附近。**

## 8. 长距离依赖探针

> **架构版本标注**：§8 的 checkpoint 为
> `data/ck_probe_sunnynet.pt`，实测其 state_dict 只含 `blocks.N.delta`，
> **不含** `theta` / `delta_max` / `delta_min` ⇒ **出自 §12 修正前的旧架构**
> （当前架构无法加载该 ckpt，会报 unexpected/missing keys）。
> 因此 §8 数值不代表修正后（残差旁路 + CSN 地板 + 可学 theta）的检索能力，
> 重新测量需在当前架构上重训。此前未标注版本，此处补正。

**探针设计**：在真实验证语料上找**重复出现的 token 片段**。若某片段曾出现过，
模型若真能利用长程上下文，就应把该片段之后曾出现的 token 排在 top-1。
按"距最近一次出现的距离"分桶统计命中率。

支持两种键长（`--ngram`）：`1` = 单 token 前驱；`4`/`8` = 多 token 片段。
键越长，命中越说明真正的长程检索而非局部平滑。

### 8.1 判别力自检

| 模型 | code_python / ngram=4 / far 桶命中率 |
|---|---|
| **未训练**（随机初始化） | **0.0** |
| 训练 800 步后（SunnyNet） | **0.1208** |
| 训练 800 步后（Transformer） | **0.1208** |

未训练模型全桶 0.0 → **探针确实测量了习得的检索能力**，不是噪声。

### 8.2 对照结果（budget：800 步 / T=1024 / batch 4 / `small` 预设）

| 键长 | 域 | 距离桶 | SunnyNet | Transformer |
|---|---|---|---|---|
| 1 | code_python | near | 0.1796 | 0.1802 |
| 1 | code_python | mid (17–256) | 0.1166 | 0.1184 |
| 1 | code_python | far (257–2048) | 0.0096 | **0.0129** |
| 4 | code_python | near | 0.3961 | 0.3943 |
| 4 | code_python | mid | 0.1143 | 0.1143 |
| 4 | code_python | **far** | **0.1208** | **0.1208** |
| 8 | code_python | near | **0.4578** | **0.4578** |
| 8 | code_python | mid | **0.1093** | **0.1093** |

| 1 | zh_ancient | near | 0.0166 | 0.0008 |
| 4 | en_literature | far | 0.0 | **0.003** |

### 8.3 读数

1. 长程检索真实存在，且在结构化文本上显著：代码域 far 桶（距离 257–2048）
   在 ngram=8 时命中 **0.134**，远高于随机（词表 8192 → 随机约 0.0001）。
2. **键越长命中越高**（near 桶 0.18 → 0.40 → 0.46）：重复片段越长，命中越可靠，
   说明模型在做片段级匹配，符合长程检索的行为特征。
3. **两个架构在重复模式上表现相当**：ngram=4 的 mid/far 桶数值**完全一致**（0.1143/0.1208）。
   这与 §7 的训练对照（SunnyNet 质量略逊 0.6%）方向一致。
4. **自然语言域远距离命中率接近 0**：这与 §9 的风险判断一致——滚动状态
   `H_max=8192` 只保证"不被遗忘"，不保证"可被检索"。自然语言的远距离依赖
   比代码的重复模式更难，本架构在此**未显示出优势**。

**边界**：`ultra` 桶（距离 >2048）在所有配置下样本数为 0，**无数据**，
§8 不对该区间作任何结论。探针在 T=1024 窗口内进行，更长跨度的能力未测。

## 10. 与同复杂度 O(N) 架构的对比

> **这一对比的必要性**：只对比 Transformer 不足以支撑"超越或持平现有公开方法"——
> Transformer 是 O(N²)，与 SunnyNet 不在同一复杂度类别。**真正的对照组是同样
> O(N) 的公开架构**：线性注意力、RWKV、Mamba、Hyena、H3。

### 10.1 对照实现

`sunnynet/linear_baselines.py` 手写实现（不调用第三方库，以保证参数量可控）：

| 架构 | 来源范式 | 核心机制 |
|---|---|---|
| `linear_attn` | 线性注意力（Katharopoulos 2020 形式） | 特征映射 `φ(x)=elu(x)+1`，因果累积 `KᵀV`，无 softmax |
| `rwkv` | RWKV-4 | 时间混合 wkv（用闭式扫描实现）+ 通道混合 `relu²` |
| `mamba` | Mamba / S6 | 输入相关选择性门控 + 因果深度卷积 + SiLU 门 |
| `hyena` | Hyena | FFT 长卷积 ×3 层 + 乘性门控 + 深度短卷积 |
| `h3` | H3-2 | 对角 SSM（闭式扫描）+ 短卷积 + 乘性门控 |

### 10.2 公平性保证

1. **参数量对齐**：以 SunnyNet 计算栈参数量（排除嵌入，因 SunnyNet 无位置嵌入）为目标。
   对齐用 meta device 实例化计数，不用手推公式——
   实测手推公式漏项严重（RWKV 偏差达 **34%**）。
2. **层数约束**：各架构层数与基准差不超过 ±1（必要时 ±2），
   避免靠"极深层数"或"极宽单层"凑参数。

### 10.4 读数（负面结论）

1. **T=256 下 SunnyNet 不优于同复杂度同行**。RWKV / Mamba / H3 三者
   ppl 均低于 SunnyNet，H3 最优（ppl 53.93，为 SunnyNet 的 **0.57×**）。
   这与 §2 的短序列劣势一致——T=256 远低于 O(N) 交叉点（T≈834），
   正是 SunnyNet 常数因子最吃亏的区间。
2. **速度优势同样未兑现**：SunnyNet ms/token 0.3277 高于 Hyena（0.2520）
   、H3（0.2793）、RWKV（0.3046）。T=256 下"O(N) 更快"对 SunnyNet 不成立，
   因为扫描的算子调度开销在小 T 下占比高（§6 已测：backward 占 74%，
   `aten::mul` 338 次/步）。
3. 与 Transformer 基本持平：ppl 93.82 vs 90.18（差 4.0%），
   ms/token 0.3277 vs 0.3394（SunnyNet 快 3.4%）。T=256 时 O(N²) 的
   attention 规模尚小，复杂度类别差异未体现。

### 10.5 三点局限

1. **未收敛，不能作最终判据**。600 步 ≈ 1.23M token，cosine 已退火到 0.1×，
   而 train loss 与 val loss 均高于退火前的平台，**七个架构都没收敛**。
   按本项目一贯标准（§5 消融因未收敛判为无效），§10.3 只能读作
   **早期样本效率**的横向排序，不能读作最终质量排序。
2. **学习率未逐架构调优**。除 Transformer 外统一 3e-3，未做 Mamba / H3
   等对本架构敏感的超参搜索。**Mamba 通常需要更低 lr**，此处可能被低估；
   反过来，也不能排除其它架构还有未搜出的更优点。
3. **单种子**。§7 已测种子噪声 ppl 极差 6.32，大于此处架构间差距的一部分
   （如 SunnyNet 93.82 与 Transformer 90.18 差 3.64）。**架构间小差距不可信**，
   只有 H3 相对 SunnyNet 的 40 ppl 差距超出噪声范围。

**结论方向**：本对比**证伪**了"SunnyNet 在短序列上超越同复杂度公开方法"的说法；
它唯一可证的优势区间仍在长序列（T≥834 的常数摊薄与 T=4096 的 12.63×）。
长序列下这五个同行是否同样受益，**未测**，列为后续工作（§10.6）。

2. **SunnyNet 对同复杂度同行的优势区间不是 512<T<2048**
   （初稿曾写"512<T<2048 领先全部同行"，与本表数据不符，此处更正）。
   按 `experiments/results/on_scaling_t8.json` 原始 ms/token 逐格排名，SunnyNet
   在七架构中位列：**T=256 第 6、T=512 第 5、T=1024 第 5、T=2048 第 4、T=4096 第 3**。

3. **T=4096 时仍未闭合**：Hyena 仍明显更快（0.52×），H3 基本追平（0.98×）。

   仍有 2 个同行不慢于它。
4. **Hyena 在所有长度都更快**（0.40–0.52×）。其 FFT 长卷积常数因子极低，

**结论**：SunnyNet 的前向延迟可证优势只有一条明确成立 ——
**T≥256 优于 Transformer**（O(N) 对 O(N²)，T 越大越显著）。
对同样 O(N) 的同行，它是**随 T 改善的追赶者而非常胜者**：
T=256 排第 6、T=4096 排第 3，全程未登顶。现有数据不支持"长序列全面领先"，
也不支持"512<T<2048 领先全部同行"——后者与本表数据直接矛盾，已作废。

> **口径差异**：本表是 **batch=1 纯前向**。训练态（batch=8、含反向+优化器）
> 的排名不同，见 §17。

## 12. 架构修正

§10 的负面结论驱动了一轮**结构性修正**。三个可测缺陷逐一 A/B 后，两个被证实、
一个被证伪。全部在 600 步 / T=256 / batch=8 / lr=3e-3 / warmup=60 下，每格
独立子进程、多种子。

### 12.1 修正一：残差旁路（最大单项收益）

原架构排除残差，块输出 $o_t$ 完全取代输入 $x_t$。实测这是**误判**：

| 配置 | seed 1234 | seed 2024 | seed 3407 |
|---|---|---|---|
| 无残差（旧默认） | 93.82 | — | — |
| **有残差（现默认）** | **67.40** | **70.72** | — |
| H3-2 参照 | 53.93 | | |

残差单项 −28.2% ppl。机制：残差提供不经过状态接力的恒等直连，深层不必仅靠
状态总线承载信息，也让欠缩放崩塌不再出现。

### 12.2 修正二：CenteredScaleNorm 地板（$s_{\min}$）

原 $s_{\min}=0.25$。实测各层 norm 输入 std 低至 $0.06$、嵌入 std 仅 $0.02$，
**全部低于 $0.25$** —— 于是所有输入都走"近常量分支"，分母恒为 $0.25$，
输出只是输入的 $4\times$ 常数缩放，**归一化从未真正发生**。

扫描（含残差，2 种子均值）：

| $s_{\min}$ | 0.250（旧） | 0.100 | 0.050 | 0.025 | 0.015 | 0.010 | 0.005 |
|---|---|---|---|---|---|---|---|
| 均值 ppl | 69.06 | 61.17 | 58.35 | 57.51 | 57.42 | 57.01 | **56.79** |

单调下降，平台出现在 `[0.01, 0.025]`（差异进入种子噪声）。**定稿 $s_{\min}=0.02$**
（平台内，旧值→新值约 −16%，同时保留优于 LayerNorm 数倍的常量保护，见 §12.4）。
`experiments/results/smin_sweep.json`、`experiments/_cell_ab.py`。

### 12.3 修正三（被证伪）：可学 decay

同行（Mamba/RWKV/H3）的衰减均可学，SunnyNet 原为冻结 buffer，推测是劣势。
改造为可学 `theta` 后实测 **99.83 / 98.65**，**比冻结的 93.82 更差**，证伪。
保留可学参数（与同行对齐的公平性所需），但收益为负。

### 12.4 头对头：修正后 CSN vs LayerNorm

CSN 修正后重测与 LayerNorm 的头对头（均带残差，3 种子）：

| 归一化 | seed 1234 | seed 2024 | seed 3407 | 均值 |
|---|---|---|---|---|
| CenteredScaleNorm（$s_{\min}=0.02$） | ~57.1 | ~56.6 | — | ~56.8 |
| **LayerNorm（对照）** | **54.90** | **54.58** | **56.58** | **55.35** |
| H3-2 参照 | | | | 53.93 |

**质量上 LN 仍略优（低 2.6%）**，但差距已从修正前的 ~12 ppl 收窄到 ~1.5 ppl，
且落在种子噪声（极差 6.32）量级内。CSN 的独立价值不在质量，而在**常量输入稳定性**：

| 输入 | CSN($s_{\min}=0.02$) | LayerNorm |
|---|---|---|
| 严格常量 $3.14159$ | max$\vert y\vert = 0$ | max$\vert y\vert = 0$ |
| 近常量（$5.0 + 10^{-7}$ 噪声） | std $=1.0\text{e-}6$ | std $=1.6\text{e-}5$ |

CSN 抑制近常量噪声放大比 LN 强 **15 倍** —— 这是"滚动状态极易在某些维度趋于常量"
这一架构特性的直接对策，也是 CSN 保留的核心理由。

### 12.5 修正后的定位（七架构同协议重测）

修正后在**完全相同协议**下重跑七架构（`experiments/battery5.sh`，
数据 `experiments/results/oncompare_*.json`），位次变化：

| 架构 | 计算栈参数 | 修正前 ppl | **修正后 ppl** | 现位次 |
|---|---|---|---|---|
| `h3` | 354,640 | 53.93 | 53.93 | 1 |
| **`sunnynet`（修正后）** | **365,844** | 93.82 | **57.83** | **2** |
| `mamba` | 367,136 | 63.34 | 63.34 | 3 |
| `rwkv` | 371,712 | 64.10 | 64.10 | 4 |
| `hyena` | 369,488 | 82.50 | 82.50 | 5 |
| `transformer` | 369,200 | 90.18 | 90.05 | 6 |
| `linear_attn` | 374,112 | 91.91 | 91.91 | 7 |

七架构其余六者数值与修正前逐字一致（它们不使用 CSN / 残差），
证明本次改动**只影响 SunnyNet**，对照公平性完好；`transformer` 的 90.18→90.05
属重跑的正常抖动。

**结论**：从"倒数第二"升至**第二**，相对 ppl 由 93.82 降至 57.83（**−38.4%**），
超越 Mamba / RWKV / Hyena / Transformer / linear_attn，
但**仍未超过 H3**（57.83 vs 53.93，差约 7%）。

同 §10.5，本对比 **600 步未收敛、单种子、lr 未逐架构调优**，
只能读作早期样本效率排序，不能读作最终质量排序。

速度侧：修正后 SunnyNet ms/token 由 0.3277 升至 **0.3960**（残差带来额外计算），
仍快于 Transformer（0.3619 是本次重测值，批间有抖动）之外多数同行——
**该耗时列跨架构横比受批次负载影响，单看本表不可靠，详见 §10.6 的进程隔离测法**。

### 12.6 修正轮的测量纪律

- 所有训练格**每格独立子进程**（`_cell_ab.py`），避免同进程累积构建的耗时/内存失真。
- 梯度矩阵（`_grad_matrix.py`）为纯前反向、确定性测量，不受负载污染。
- `s_min250` 格复现了此前记录的 67.3976 / 70.7208，确认实验可复现。

## 13. 训练速度专项

**问题**：§2 的"交叉点""22.69×"均为 **batch=1 前向**，而 CPU 训练关心的是**训练速度**。
两者排序完全不同，不可互相引用。此处补测**训练步（前向+反向+更新）**。

协议：`small` 预设、batch=8、8 线程、**每格独立子进程**（§2.4 纪律）、
重复 5 次取中位数、`experiments/on_scaling.py --backward`。

| `transformer` | 0.2041 | 0.2540 | 0.5396 | 1.0792 | — |

### 13.2 结论：训练速度对 O(N) 同行全面落后

- **只在 T=256 对 Transformer 领先 1.10×**，其余全部落后。
- 对同复杂度同行：**mamba 快 20–56%、h3 快 24–29%、hyena 快 27–52%**，
  且这一劣势**从 T=256 到 T=4096 全程存在、无交叉点**。
- **旧报的"T=256 训练时 SunnyNet 快 8.4%"（§3）已作废**：那是修正前栈、未做进程隔离的测量。

> 这是明确不利的结果。已确认的质量优势（ppl 第二）与
> 速度劣势（同行快 20–50%）同时成立——当前架构是"质量换速度"，不是"又快又好"。
>
> **后续（§16，同轮）**：§13 结论**仅对 `small`（dim=128）配置成立**。
> 经**窄残差流（dim 128→80）+ `p.clamp` 构造期判掉**两条等价改动后，
> 训练步 T=256 追平 rwkv（0.0953 vs 0.0982 ms/tok，名义快 3.0%）、T=512 慢 3.7%，
> 对 h3/mamba/hyena/linear 稳定领先 16–41%。**"全面落后"在旧配置下依然成立，
> 但不再是当前架构的最优读数**；同时 T≥1024 的同行优势**未被消除**，见 §16.5。

### 13.3 根因（逐项实测排除，均不可作为改进方向）

| 假设 | 实测 | 判定 |
|---|---|---|
| 计算量更大 | MAC/token：SunnyNet **8064** ≈ mamba 7029，远低于 Transformer 55224 | **否** |
| 分块扫描块数过多 | `chunk=64` 已最优；放大块长反而更慢（原版 cumsum 沿 stride=N 维归约） | **否** |
| 线程数未调优 | 4/6/8 线程交叉测量：1483 / 1510 / 1518 ms，差异在噪声内 | **否** |
| 算子改写可省 | `_compete` 切片、`_feedback` 内联、CSN 两步 var 差异均 < IQR | **否** |

**实际根因**：
1. **算子数量**（非 FLOPs）。SunnyNet 每前向 `aten::mm` 63 次批次调用，
   另有 `mul` 762 / `add_` 376 / `fill_` 341 次/步的**小张量逐元素算子**；
   短序列瓶颈是算子调度与访存，不是计算。
2. **块内宽度最小**。SunnyNet `dim=128 / inner=192`，同行在等参数下
   `d_model` 为 88–112 但**内层更宽**（如 hyena d_ff=224），matmul 效率更高。
3. **反向占训练步 64.6%**（前向 480 ms vs 训练步 1357 ms，T=1024 B=8），
   而扫描仅占前向 12–13%——**优化扫描对训练速度几乎无用**。

### 13.4 本机可用的加速手段

| 手段 | 状态 |
|---|---|

### 13.5 实测否决的优化（勿重犯）

**块内转置扫描**（把 cumsum 转到末维，利用步长 1 归约）：
- 在隔离测试的 `N=512` 维度下扫描快 3.4×，看似大收益；
- **但真实块维度 `dim=128` 下反而慢 26.2%**（12.11 → 15.29 ms）；
- 端到端训练步**净持平**（前向 −7% 被反向 +4% 抵消）。
- 已回退，`sunnynet/ops.py` 保持原版。**扫描基准必须用真实块维度（dim=128），
  不能用隔离测试的大维度（N=512）——两者结论相反。**

**竞争门控 `roll` → `index_select`（GPU/CPU 双平台重测，§15.6/15.7）**：
- 纯门控微基准：index_select 更快（cuda 0.717×、cpu 0.891×），数值完全等价（maxdiff=0）；
- 端到端训练步：两平台均无稳定差异（cuda 5.8% 在轮间极差内，cpu 0.2%）；
- 已回退，`sunnynet/layers.py` 的 `_compete` 保持 `roll`。
- 同型教训重现：算子级微基准的优势会被端到端摊薄进噪声，不能单独作为采纳依据。

### 13.6 优化方向

1. **抬高 `h_min`（2.0 → 8/16）**：放宽 `_safe_chunk` 块长上限 64 → 332/687，
   减少 Python 循环次数。**但实测扫描耗时不降**（块数不是瓶颈），
   且改动会移动衰减谱 → 须同步质量回归。**收益不确定。**
2. **减少块内算子数量**：需算子融合。`torch.compile` 不可用，但 w64devkit 已具备，
   改由手写 AVX2 内核实现（§21/§22）。
3. **加宽块内维度**（`dim` 128 → 160/192）提升 matmul 效率：
   会破坏当前 ±1% 的参数对齐，需重做全部对照 → 成本高，但**方向最直接**。
4. **降低反向成本**：反向 64.6% 来自 autograd 图，需要算子级融合才能改善。

> **§14 实现其中两条**：方向 2 用 oneDNN 现成核落地，方向 3 的"加宽 dim"
> 在不破坏参数对齐的前提下实现（见 §14.3 减层加宽）。

## 14. 算子融合与减层加宽

### 14.1 唯一可行的融合路径：oneDNN 现成核

`torch.compile` / Inductor 不可用（§13.4 已修正为"MSVC 存在但 SDK 头文件缺失"）。
CPU 上真正可用的融合是 **oneDNN 的原生融合算子**——`F.layer_norm` 把
mean/var/sub/mul/add 融成单 kernel。

- `CenteredScaleNorm` 在 `c = 0` 时与 gamma-scaled LayerNorm **严格等价**
  （`gamma/center` 与 LN 的 `weight/bias` 是同一角色）。改走 `F.layer_norm` 后：
  - 前向 4.535 ms → **0.232 ms（19.5×）**；反向 11.075 → 2.485 ms（4.46×）
- **两级并行扫描** `gated_scan`：把"逐块串行 ceil(T/chunk) 次 Python 循环"改为
  "块内一次 cumsum 覆盖全部块 + 块间串行 nblk 步"，fp32/fp64 均 **bit-identical**。

端到端训练步（`experiments/_speed_ab.py`，每格独立子进程、多轮中位）：

| T | 提速 |
|---|---|
| 256 | −19.3% |
| 512 | −24.4% |
| 1024 | −18.9% |
| 2048 | −29.4% |
| **4096** | **−41.2%** |

**质量同步提升**（600 步三种子，`_quality_ab.py`）：

| 实现 | seed1234 | seed2024 | seed3407 | 均值 ppl |
|---|---|---|---|---|
| 旧（手写 CSN + 串行扫描） | 92.96 | 90.46 | 92.71 | 92.04 |
| **新（融合 LN + 并行扫描）** | 84.36 | 83.81 | 84.95 | **84.37** |

⇒ **质量与速度同时变好**，43→47 项测试全绿。

### 14.2 关键发现：参数对齐下 SunnyNet 层数远超同行

meta device 实测（真实计数，非手推公式）：

| 规模 | SunnyNet | mamba | h3 | hyena | rwkv | linear_attn |
|---|---|---|---|---|---|---|
| proto20m（栈 16.77M） | **L=10** | L=5 | L=5 | L=7 | L=6 | L=6 |
| p100m（栈 93.74M） | **L=14** | L=7 | L=8 | L=9 | L=7 | L=7 |

- 这**偏离项目自身公平性纪律**（"层数偏离基准 ≤±1，必要时 ±2"），超出 +3~+8 层。
- 成因：低秩（`rank/dim ≈ 0.6`）+ 窄 `dim` → 单层参数少 → 参数对齐下被迫堆深。
- 后果：层数多 = **每层算子集合 × 更多次** ⇒ 直指 §13 根因①"算子数量"。

### 14.3 减层加宽（栈参数量对齐下）

在**栈参数偏差 ±0.1%** 前提下把层数压回同行档、同时加宽 `dim`：

| 预设 | 配置 | 栈参数 | T=256 ms/tok | T=512 ms/tok | 峰值 RSS |
|---|---|---|---|---|---|
| proto20m | d512 i896 r320 **L10** | 16,766,514 | 1.262（5 轮中位） | 1.330 | 2253 / 3817 MB |
| **proto20mw** | d640 i1280 r384 **L6** | 16,755,230（+0.07%） | **1.110（−12.1%）** | **1.108（−16.7%）** | **1935 / 3240 MB** |
| p100m | d1024 i1792 r640 **L14** | 93,738,054 | 4.957 | OOM | 5802 MB |
| **p100mw** | d1408 i1920 r1024 **L8** | 93,828,904（+0.10%） | **4.158（−16.1%）** | 3.969 | **4897 MB** |

- 工具 `experiments/_rebalance_probe.py`（每格独立子进程）；预设 `proto20mw` / `p100mw` 已入 `train/train.py`。
- 反序复测排除顺序效应：**5/5 轮 proto20mw 更快**。
- 加速 12–17%，与"层数减 40%"量级吻合 ⇒ 根因是算子数量（层数），不是 FLOPs；
  顺带把层数拉回同行档，**修复了公平性缺陷**。

### 14.4 质量验证：减层加宽同样是双赢（20M / T=256 / 400 步 / 真实语料）

| 预设 | L | dim | 栈参数 | 100 步 ppl | 200 | 300 | 400（best） | 墙钟 |

### 14.7 核心扫描 / 竞争门控写成融合 kernel 的收益上界

**问题**：把核心扫描与竞争门控写成融合 kernel 会不会显著更快？

**方法**：`experiments/_fuse_ceiling.py` 把这两段各替换为极简实现（数值不等价），
测端到端训练步。这给出"两段耗时归零"的**收益上限**，不是可落地的改写。
small 预设、T=1024、B=8、每格独立子进程、两轮交错取中位：

| 变体 | ms/token | 相对基线 |
|---|---|---|
| base（当前） | 0.1575 | — |
| 竞争门控耗时归零 | 0.1465 | −7.0% |
| 扫描耗时归零 | 0.1476 | −6.3% |
| **两者同时归零（上界）** | **0.1436** | **−8.8%** |

**结论**：

1. **替换实验给出的收益上界为 8.8%**（把两段耗时直接归零，数值不等价，仅测上限）。
2. **§21/§22 的落地实测超出该上界**：w64devkit 打通 AVX2 内核后，融合内核
   训练步实测 1.10–1.17×（§22.3/§22.6）。上界估计偏低的原因是该实验在
   `small/T=1024` 口径下做，而落地测的是 `smalln80/T=256–512`（scan 占比更高）。
3. **单块剖析解释了占比来源**：`_compete` 占单块 14.4%、`_scan` 占 17.2%（前向），
   而**训练步的反向占约 65%**（§13.3），前向占比再高也摊不进大分母。
4. **实务判断**：融合内核的实测收益（1.10–1.17×）低于减层加宽（12–17%），
   但两者可叠加。

### 14.8 100M 规模同协议对照（部分架构在高 lr 下发散）

`p100mw` 预设（dim=1408/inner=1920/rank=1024/L=8，栈 93,828,904），
T=256、B=8、100 步、统一 lr=3e-3、同语料，同行按栈参数对齐（`n_layers=8`）：

| 架构 | 栈参数 | 偏差 | ppl | ms/token | 状态 |
|---|---|---|---|---|---|
| rwkv | 94,115,520 | +0.31% | 105.66 | 3.351 | 正常 |
| **sunnynet** | 93,828,904 | — | **109.47** | 4.657 | 正常 |

| hyena（lr=3e-3） | 93,674,760 | −0.16% | — | — | **gn≈41.5 梯度爆炸** |

**两个负面事实**：

1. **统一 lr=3e-3 在 100M 下对 mamba/hyena 过大**。这不是 SunnyNet 的优势，
   属对照协议的缺陷：lr 未逐架构调优（§13 已声明该限制）。

   证实前述发散是**优化器步长问题，不是架构缺陷**。
2. **SunnyNet 100M 的 ppl 只到第二**（109.47），落后 rwkv（105.66）约 3.6%（相对
   rwkv），领先 h3 约 14.6%。**20M 时的"质量第一"在 100M 没有延续**——
   scaling 趋势不是单调变好，现有数据不支持"规模越大越有优势"。

**旁证：训练器缺失的防御**。mamba 发散时 `_safe_chunk` 在 `p_min=NaN` 处
`int(NaN)` 抛 `ValueError`，使整个对照进程崩溃、无任何结果落盘。
已修：`_safe_chunk` 先判 `isfinite`；训练器在 loss/grad_norm 非有限时
打印 `[发散]` 并优雅中止，把 `diverged` 写入 summary（此前是静默死掉）。

**hyena 的段错误**：hyena@100M 在本机多次以 SIGSEGV（exit=139）中止，
且**与步数无确定关系**（steps=5/20 崩、steps=50 通过；B=2/4 通过、B=8 有时通过）。
排查确认**不是架构缺陷**：同配置单独、低线程下可通过；崩溃发生在进程峰值 RSS 达
5977–6131MB 时，属本机内存/页文件压力下的偶发（§14.5 的 15.9GB 物理内存约束，
且 C 盘仅剩 7GB、页文件难以增长）。
**因此 100M 的可比对照为 4 个架构**（sunnynet / rwkv / h3 / mamba-lr1e3），
hyena 记为"本机不可稳定完成"——**无其数值**。

## 15. GPU 验证与 0.5B 规模化

### 15.2 SunnyNet 在 GPU 上可运行，且扫描/门控无 CUDA 特化失败

`experiments/_gpu_probe.py`（每格独立子进程），B=8：

| small | 1024 | 439.3 ms | 28.9 ms | **15.20×** | 1186.3 ms | 99.0 ms | **11.99×** | 1562 MB |

（原始数据 `experiments/results/gpu_compare.json`。）

**结论**：

1. **架构在 GPU 上可直接运行**——核心两级并行扫描（`cumsum`/`exp`）与竞争门控
   （`sigmoid` 成对）都是标准 CUDA 算子，无需任何 CUDA 特化改写即通过，
   这说明 GPU kernel 的坎不在能否运行，在**性能要不要特化**。

3. **但这是消费级老 GPU（GTX 1060，6GB）**，且**未做任何 CUDA 侧优化**

4. **§15.2 未测 GPU 上的同行对照**，因此不支持"GPU 上快过同行"的说法
   （Mamba/H3 等在 GPU 下的官方实现未测）。

### 15.3 0.5B（scale05b）阶梯测试——GPU 上可跑，但训练受显存硬约束

`experiments/_05b_gpu_ladder.py`，参数 **498,464,858 总 / 481,687,642 栈**：

| 级别 | 内容 | 结果 | 峰值显存 |
|---|---|---|---|
| L1 | 构建到 cuda（fp32） | **通过**（80.7 s） | 1902 MB |
| L2 | 前向 B=1 T=512 | **通过** | 1978 MB |
| L3 | 前向 B=1 T=1024 | **通过** | 2044 MB |
| L4 | **SGD 训练步** B=1 T=512 | **通过**（loss 9.48） | 4426 MB |
| L5 | **AdamW 训练步** | **OOM**（T=64/128/256 均失败） | >6144 MB |

**结论**：

1. **0.5B 前向与 SGD 训练在 6GB GPU 上可跑通** —— §14.5"0.5B 本机不可能运行"
   应限定为：**在 CPU fp32 上不可实例化；在 GPU 上前向/SGD 可运行**。
2. **AdamW 不可行**：权重 1.9GB + 梯度 1.9GB + AdamW 两个动量状态（≈3.8GB）= 7.6GB 超 6GB，
   在当前显存下**无法做完整优化器训练**。可行路径是梯度累积 + SGD，
   或显存更大的卡，或分片优化器——**本次均未验证**。
3. **无"0.5B 训练跑通"的结论**：只跑通了 SGD 单步，没有跑过多步收敛，
   也没有任何 0.5B 质量数据。

**阶梯脚本的口径缺陷（已定位）**：`_05b_gpu_ladder.py` 在同一进程内先跑 T=512/T=1024
前向后跑训练步，**显存碎片**使 L4/L5 报 OOM。改为独立子进程单跑 L4 后：
**SGD 单步通过**（峰值 5004 MB，剩余 563 MB，loss 9.4274）。
⇒ 阶梯脚本的 OOM 读数是碎片造成的假阴性，**每档必须独立子进程**（与 §2.4 的 CPU 侧纪律同源）。

**优化器状态 offload 尝试（`experiments/_05b_offload.py`，未成功）**：
把 AdamW 的 m/v 常驻 CPU、按张量搬运，理论额外显存仅一个参数张量。
实测失败——本机物理内存只剩 4.5GB，分配 3.71GB 优化器态即触发 `Memory allocation failure`，
页文件压力连带使 CUDA 上下文报 `unknown error`。
改用 bf16 存优化器态（1.86GB）后仍 OOM，卡在激活侧（`gated_scan` 的 `exp(P)` 分配 20MB 失败）。
⇒ **本机不具备 0.5B AdamW 训练的内存条件**，与显存无关，是主机物理内存不足。

### 15.4 0.5B 多步训练探针（`experiments/_05b_train.py`，真实语料）

**动机**：§15.3 只回答"能跑到第几级"。此处补多步，看 loss 是否真的在动。

配置：`scale05b`（498,464,858 参数）、**无动量 SGD**、T=128、B=1、lr=1e-3、
30 步、数据取自 `data/proc` 三个域的真实 token 流（非随机 token）。

| 步骤 | loss | grad_norm |
|---|---|---|
| 1 | 9.3152 | 36.4 |
| 2 | 9.2628 | 34.0 |
| 3 | 9.4613 | 155.1 |
| 10 | 9.1438 | 40.6 |
| 20 | 8.9834 | 52.0 |
| 30 | 9.3103 | 25.9 |

峰值显存 4425 MB（6GB 卡），构建 87.8 s。

**结论**：

1. **loss 在噪声里震荡，30 步看不到下降趋势**（首 9.3152 → 末 9.3103，
   Δ=−0.005，而步间极差达 0.72）。这**不是收敛数据**，只是"机器能跑、梯度有值"。
2. **grad_norm 大且不稳**（24–155）。0.5B + lr=1e-3 + 无 warmup 属欠标定；
   不能据此评价架构，9.31 **不能作为 0.5B 的 ppl/token 质量**引用。
3. **无动量是显存妥协**：加 `momentum=0.9` 即 OOM（权重 1.9 + 梯度 1.9 + 动量 1.9 ≈ 5.7GB
   逼近 6GB）。即 6GB 卡的 0.5B 只能跑最朴素的 SGD。
4. **梯度累积未验证**——若要真正训练 0.5B，需梯度累积或分片优化器，本机均未测。

**补充：T=64 复测与稳定性边界**（加 warmup 5 步、lr=1e-3、30 步）：

| 步骤 | loss | grad_norm |
|---|---|---|
| 1 | 9.3587 | 41.8 |
| 20 | 7.7206 | 61.9 |
| 30 | 9.2953 | 34.4 |

首 9.3587 → 末 9.2953（Δ=−0.063），**仍在噪声内**（步间极差 1.87，如 step20 的 7.72 是
单次波动，不是下降）。峰值显存 4118 MB。

**稳定性结论**：**0.5B 在 6GB 卡上属于边界态，结果不可复现**——
同一配置（lr=1e-3、T=128）三次运行：一次 30 步全部通过、两次第一步 backward 即 OOM
（仅 3.74GB 分配就失败，而 `nvidia-smi` 显示 6031MB 空闲）。
根因是 **WDDM 平台的显存分配悬崖**（torch 明确警告
`expandable_segments not supported on this platform`），不是模型缺陷。
因此：**0.5B 只能用于"前向/单步正确性验证"，不能用作可复现的训练基准**。
调大 lr 至 3e-3 时第一步 backward 必 OOM（激活随权重更新膨胀）。

### 15.5 GPU 侧算子剖析：融合的收益空间比 CPU 更小

**动机**：§14.7 的 8.8% 上界是在 CPU 上测的。GPU 上算子成本结构完全不同，
需重测才能回答"GPU 上融合值不值得"。

方法：`experiments/_gpu_profile.py`，small 预设、T=512、B=8、
`torch.profiler` 按 CUDA kernel 聚合 self time，取 12 次平均。

| 类别 | 前向（eval） | 训练步 |
|---|---|---|
| `cumsum`/scan 类 | **1.85%** | **1.22%** |
| `sigmoid`/竞争门控类 | **2.55%** | **2.02%** |
| `aten::mm` + cuBLAS sgemm | 32.8% | 28.6% |
| `aten::roll` | 3.13% | 1.91% |
| 前 8 大算子合计 | 51.1% | 53.6% |

**结论**：

1. GPU 上这两段的占比比 CPU 低一个量级。CPU 上前向 `_compete` + `_scan` 约 31.6%
   （§14.7 单块剖析），GPU 上两者相加不足 5%（被 GEMM 稀释）。
   因此"融合 kernel"在 GPU 上的收益空间比 CPU 更小，不是更大。
2. **GPU 上没有单一支配算子**（最大 `aten::mm` 16.4%），与 CPU 侧结论一致：
   只能靠减少**算子数量**改善，而本机无 nvcc / 无 CUDA toolkit / 无 triton
   （`torch.utils.cpp_extension` 连 `setuptools` 都缺），无法编译任何自定义 kernel。
3. 本机 GPU 只用于"验证正确性 + 加速比"，不用于内核级优化，这是本机的能力边界。

### 15.6 附：竞争门控 `roll` → `index_select` 的分平台实测

**背景**：GPU 剖析发现 `aten::roll` 占 3.13%（前向）。CPU 上"roll→切片"曾被
否决（记入否决清单）。两平台成本结构不同，故**分平台重测**。

微基准（`experiments/_compete_bench.py`，纯门控、数值等价性同脚本验证）：

| 平台 | roll | index_select | 比值 | 前向 maxdiff | 梯度 maxdiff |
|---|---|---|---|---|---|
| cuda | 2349.7 µs | 1683.8 µs | **0.717** | 0.0 | 0.0 |
| cpu | 15518.8 µs | 13819.9 µs | **0.891** | 0.0 | 0.0 |

两平台的微基准都指向 index_select 更快，且数值完全等价——与 CPU 上旧的
"roll 更优"结论相反。微基准单独不足以定论，需端到端判定
（§14.4 已多次出现微基准与端到端不一致的情况）。

端到端 A/B（`experiments/_compete_e2e.py`，每格独立子进程、两轮交错）结果见
§15.7；**以端到端为准**。

### 15.7 竞争门控改写端到端判定

`experiments/_compete_e2e.py`，small、T=512、B=8、训练步、每格独立子进程、两轮交错。
数值一致性：两实现 loss 完全相同（cuda 9.034 / cpu 9.035），改写**不损质量**。

| 平台 | roll 两轮 | index 两轮 | 中位差 | 结论 |
|---|---|---|---|---|
| cuda | 59.57 / 56.87 ms | 58.62 / 64.58 ms | roll 快 5.8%（轮间极差 13.5%） | 噪声内 |
| cpu | 548.1 / 520.6 ms | 519.9 / 547.0 ms | 持平（0.2%） | 无差异 |

结论：端到端两平台均无稳定差异，不采纳改写，维持 `roll`。

同型教训再次出现：纯算子微基准说 index_select 更快（cuda 0.717×、cpu 0.891×），
**端到端却测不出差异**。原因是门控算子只占端到端很小份额（GPU 前向 2.55%、
CPU 前向约 14%），微基准的收益被摊薄进噪声。**微基准不能单独作为采纳依据**
——与 §14.4 的多次结论一致。此条并入否决清单。

## 16. 训练速度追平同行

**背景**：§13 记录"训练速度对 O(N) 同行全面落后 20–52%"，是项目长期唯一未拿下的指标。
§16 用两条**等价**改动把它追平。目标：训练速度持平或超越同行。

### 16.1 等价优化 A：`p.clamp` 构造期判掉

`_core` 里 `p = 1 - delta*(1 - sigmoid(gate))` 带 `p.clamp(p_floor, 1.0)`。
解析下界：`delta = 1/H ≤ 1/h_min`，故 `p ≥ 1 - 1/h_min = p_min_bound`；
且 `sigmoid(gate) ∈ (0,1) ⇒ p < 1`。上界恒成立，下界在 `p_min_bound > p_floor` 时恒不触发。

| 量 | 值（`small`，h_min=2.0 / h_max=2048.0） |
|---|---|
| `p_min_bound` = 1−1/h_min | **0.5** |
| `p_floor` = 1/h_max | 4.883e-4 |
| 实测 p 区间（20 步 × 4 层采样） | **[0.5902, 0.99994]** |

真实下界 0.5902 比 `p_floor` 高 **1209×**，clamp 不可达。改为构造期判定 `_need_clamp`：

```python
self._need_clamp = self.p_min_bound < self.p_floor
```

- **等价性**：去 clamp 前向逐位相等（`maxdiff = 0.000e+00`，`experiments/_clamp_check.py`）。
- **收益**：消除反向图里的 `ClampBackward1` 节点（原 `aten::clamp_backward` 59.5 ms / 12 步，
  占 1.7%）及其前向 `clamp` 的张量往返。`h_min=1.0` 时判定自动回退为 `True`，行为不变。
- 新增 3 项性质测试（`_need_clamp` 真/假两侧 + 实测 p 落在解析界内），测试 51 → **54** 全绿。

### 16.2 等价优化 B：窄残差流配置（`smalln80` / `smalln88`）

§13.3 归因"逐元素算子按**激活宽度**付费（宽度由 `dim` 决定）"。等栈参数（~365k）下压 `dim`：

| 预设 | 配置 | 栈参数 | 偏差 |
|---|---|---|---|
| `small` | d128 i192 r64 L4 | 365,844 | 基准 |
| `smalln96` | d96 i192 r152 L4 | 363,860 | −0.54% |
| `smalln88` | d88 i176 r196 L4 | 365,924 | +0.02% |
| **`smalln80`** | **d80 i160 r244 L4** | **365,940** | **+0.03%** |

`experiments/_train_bench.py`：每格独立子进程 + 交错多轮 + 取中位（§2.4 纪律）。
T=256、B=8、8 线程、5 轮、ms token = 2048/步。

### 16.3 结果：训练步速度（ms/token，越低越好，5 轮独立子进程中位）

| 架构 | 栈参数 | **T=256** | **T=512** |
|---|---|---|---|
| **sunny80** | 365,940 | **0.0953** | 0.0986 |
| rwkv | 361,920 | 0.0982 | **0.0951** |
| sunny96 | 363,860 | 0.1011 | 0.1090 |
| sunny88 | 365,924 | 0.1013 | 0.1089 |
| h3 | 369,760 | 0.1138 | 0.1239 |
| sunny128（旧） | 365,844 | 0.1158 | 0.1243 |
| mamba | 364,960 | 0.1292 | 0.1271 |
| hyena | 392,760 | 0.1312 | 0.1468 |
| linear_attn | 364,720 | 0.1569 | 0.1676 |

**相对旧配置（`small` / dim128）**：T=256 **−17.7%**，T=512 **−20.7%**。

### 16.4 head-to-head：sunny80 vs rwkv（逐轮配对，9 轮独立子进程）

单一中位数会被"轮间漂移"误导，故补**逐轮配对**（每轮 sunny80 与 rwkv **在相邻时刻各跑一次**）：

| 指标 | T=256 | T=512 |
|---|---|---|
| sunny80 中位 | 204.7 ms（0.0999 ms/tok） | 466.5 ms（0.1139 ms/tok） |
| rwkv 中位 | 215.5 ms（0.1052 ms/tok） | 475.8 ms（0.1162 ms/tok） |
| **配对比值 中位（s/r）** | **1.042** | **1.006** |
| sunny80 **更快轮数** | **3 / 9** | **4 / 9** |

三个指标互相矛盾 ⇒ 结论是"统计持平"，不是"超越"：
中位数 ratio-of-medians 偏 sunny80，但配对中位比值与符号检验都指向 rwkv，
且两架构轮间极差（rwkv 单轮 171–253 ms）远大于两者中位差。**这一读数原样保留。**

### 16.5 四项局限

1. **速度仅在 `L=4` 下持平**。层数对齐到 rwkv 的 `L=6` 时，同预算的窄配置
   （d56/d64/d72）**反而慢 30–40%**（260–342 ms vs rwkv 225 ms）——
   同预算下压 `dim` 到 56–72 使层数负担压过宽度收益，**瓶颈是算子数量而非 FLOPs**。
   本项目现有对齐协议按"栈参数量"，不约束层数，故 §16.3 的持平建立在 SunnyNet 用更少层上。
2. **T=256 是最佳点**：此处 `smalln80` 胜过 rwkv；T=512 已转为 rwkv 微快。
   **不可外推到长序列**——§13 已证 T ≥ 1024 时同行优势扩大。
3. **质量代价**：`smalln80` 的 600 步多种子 ppl **62.37**（d80）vs 旧配置 54.89（d128）。
   代价换来的是速度持平。这不是"又快又好"，是速度-质量权衡点前移。
4. **lr 未逐架构重调**、单机单线程数（8）、单一实现（手写基线），与其他节同。

### 16.6 速度-质量帕累托前沿（T=256，栈参数均 ~365k）

| 预设 | dim | ppl（600 步 3 种子均值） | ms/tok | 定位 |
|---|---|---|---|---|
| `small` | 128 | **54.89** | 0.1158 | 质量最好 |
| `smalln96` | 96 | 58.84 | 0.1011 | 折中 |
| `smalln88` | 88 | 61.90 | 0.1013 | **被 96 支配**（同速、质量更差） |
| `smalln80` | 80 | 62.37 | **0.0953** | 速度最好 |

同行参照（600 步、单种子 1234）：h3 **53.93** / mamba 63.34 / rwkv 63.86 / linear 91.91。

- **`smalln88` 被 `smalln96` 支配**：同速却质量更差 → 已从预设清单剔除候选。
- 速度优先 + 质量不劣于同速同行：取 `smalln80`——速度 0.0953 与 rwkv 持平，
  600 步 ppl 62.37 **优于 rwkv 63.86 与 mamba 63.34**。⇒ 这是一个**同时不吃亏**的点。
- **质量优先**：仍用 `small`（0.1158），代价是比 rwkv 慢约 15%。
- **`smalln88` 的设计意图**（保留 dim 更低但 rank 更宽）**实测无效**。

### 16.7 结论

- **训练步速度达成"持平"**：`smalln80` 在 T=256 **名义快于 rwkv 3.0%**、T=512 慢 3.7%，
  配对检验不显著（3–4/9 轮占优）。按项目纪律，结论为"与 rwkv 统计持平"，
  不读作"超越"。
- **对 h3 / mamba / hyena / linear_attn 是稳定领先**：T=256 快 16–39%，
  T=512 快 20–41%（各架构中位差均大于轮间极差）。
- 对 Transformer 早已领先（§13 的 1.10× 现扩大，因其 T 依赖 ∝T 而 SunnyNet ~O(N)）。
- **§16 不改变**：长序列（T≥1024）同行优势仍在；质量排序 `small` 仍是七架构第二；
  §13 的 T=256→T=4096「全面落后」在**旧 dim128 配置**下依然成立。

**对照目标**：训练速度持平或超越同行——**持平达成（rwkv / h3 / mamba / hyena /
linear_attn / transformer），超越未达成（rwkv 仅名义领先）**。

## 17. T=1024 训练态速度与峰值内存审计

**触发**：质疑"T=1024 区间速度最慢、峰值内存最高"。
**既有数据的缺口**：§10.6 只测了 **batch=1 纯前向**，且**从未记录过内存**。
§17 的 `experiments/_T1024_audit.py` 补这两块——训练态（前向+反向+AdamW 步） 与
**激活内存峰值**。协议：batch=8、T=1024、8 线程、每格独立子进程、只构建一个模型。

速度（ms/token，越小越快）：

| 架构 | ms/token | 七架构排名 |
|---|---|---|
| **sunnynet** | **0.13186** | **1** |
| h3 | 0.13190 | 2 |
| mamba | 0.14721 | 3 |
| hyena | 0.16754 | 4 |
| linear_attn | 0.17646 | 5 |
| rwkv | 0.19677 | 6 |
| transformer | 0.55693 | 7 |

峰值内存（建完模型后的 current_rss 为基线，peak_rss 为高水位；`act` = 两者之差）：

| 架构 | peak RSS | 排名（大→小） | 激活峰值 | rss_alloc（固定） |
|---|---|---|---|---|
| transformer | 3192 MB | 1 | 2769 MB | 423 MB |
| **sunnynet** | **1812 MB** | **2** | 1521 MB | 291 MB |
| hyena | 1809 MB | 3 | 1513 MB | 296 MB |
| mamba | 1780 MB | 4 | 1485 MB | 294 MB |
| linear_attn | 1777 MB | 5 | 1482 MB | 295 MB |
| h3 | 1689 MB | 6 | 1394 MB | 295 MB |
| rwkv | 1611 MB | 7 | 1317 MB | 295 MB |

**读数（与 §10.6 的口径差异是关键）**：

1. **训练态（batch=8，含反向）与 batch=1 纯前向的排名完全不同**。纯前向 T=1024 时
   SunnyNet 排第 5（§10.6）；训练态下它**排第 1**（0.13186，与 h3 的 0.13190 实质并列）。
   原因是反向占训练步 56.9%（§13.3），而 O(N) 同行的反向含大量逐元素链，
   在 batch=8 下比 SunnyNet 更吃亏；Transformer 的 O(T²) 注意力反向最贵（0.557，慢 4.2×）。
2. "SunnyNet 内存最高"不成立：它的峰值 RSS（1812 MB）在七架构中排**第 2**，
   仅高于 5 个 O(N) 同行 0–12%，**比 Transformer 低 43%**（1812 vs 3192）。
   内存最高的是 Transformer（激活 2769 MB），因其注意力需保存 O(B·H·T²) 的中间量。
3. **激活内存是主要项**：七架构的 `rss_alloc`（参数+优化器+输入）都在 291–423 MB，
   差异全部来自激活。SunnyNet 的激活 1521 MB **高于四个同行**（h3 1394 / rwkv 1317 /
   linear_attn 1482 / mamba 1485），因它保存整段扫描状态 `(B,T,d)`（§4.2 已记录该机制），
   但 Henry 类（hyena）与它同档，Transformer 远高于它。
   即：SunnyNet 的内存在 O(N) 同行中偏高、比 Transformer 显著低，并非最高。
4. **与质疑的逐条对照**："T=1024 速度最慢 + 内存最高"，
   **前提是 batch=1 纯前向**——该口径下 §10.6 显示它排第 5（不是最慢，
   transformer 垫底），但确实慢于 4 个同行；内存则**在任何口径下都非最高**。
   训练态口径下两个指控都不成立。

**局限**：§17 测的是随机初始化模型的单步开销（速度与内存**与模型质量无关**，
故用随机 token 不损结论）；AdamW 状态使 `rss_alloc` 比 SGD 高，但七架构同口径可比。

**协议**：原三域混合（0.4/0.35/0.25）训练 600 步，batch=8，T=256，lr=3e-3，

1. **单种子、600 步未收敛**：与 §10.5 同限制，只能读作早期样本效率排序。

3. **新域规模有限**（arxiv 236K / news 165K token），且 `arxiv_en` 是**摘要**而非全文，
   与原文书的长度分布不同。
4. **未做域平衡**：新域测试集全部来自单一来源，未覆盖"新域但同体裁"的中间情形。

**结论**：在**外部独立数据集**上，SunnyNet 的绝对 ppl 落在七架构第一档 ——
`zh_tech_news` **第 1**（321.08，在 unk 23% 的不利条件下）、`arxiv_en` **第 2**（35.58）；

反向主张"泛化能力强"同样不成立——绝对 ppl 仍高（英文新域 35.58、中文新域 321），
600 步未收敛、单种子，且 §18.2-3 已说明中文域的比值口径陷阱。
§18 的可靠结论只有一条：**跨分布表现不比同复杂度同行差**。

## 19. 短序列倒挂：训练态核查与缓解幅度

**触发**：反馈称"T<384 时慢于 Transformer，限制其在短句分类/对话回复等常规任务中的应用"，
要求"弥补完善"。**该说法基于 batch=1 纯前向口径（§2.4 交叉点 T≈384）**，
但那些任务实际是**训练/微调**场景（含反向、batch>1），故按训练态复测。

脚本 `experiments/_shortseq.py`：batch=8、训练步（前向+反向+AdamW）、
每格独立子进程、3 轮交错取中位。

**训练态 ms/token 中位（3 轮）**：

| 配置 | T=128 | T=256 | T=384 |
|---|---|---|---|
| `small`（d128 i192 r64 L4） | 0.13009 | 0.14094 | 0.15241 |
| `smalln80`（d80 i160 r244 L4，§16） | **0.12315** | **0.10675** | **0.11148** |
| `transformer`（栈对齐 6 层） | 0.11785 | 0.20975 | 0.26238 |

**相对 Transformer 的比值（>1 = 比 TF 慢）**：

| 配置 | T=128 | T=256 | T=384 |
|---|---|---|---|
| `small` | 1.104 | 0.672 | 0.581 |
| `smalln80` | **1.045** | **0.509** | **0.425** |

**读数**：

1. **训练态交叉点比前向下移很多**：前向（batch=1）交叉点 T≈384（§2.4），
   训练态（batch=8）下 **T=256 已完成反超**（`small` 0.672、`smalln80` 0.509）。
   这与 §2.3 "交叉点随 batch 增大向更小 T 移动"一致，并把它量化了。
2. **T=128 仍然倒挂，但幅度很小**：`small` 慢 10.4%、`smalln80` 慢 **4.5%**。
   注意这档落在**内存高压测量**的噪声带内（本次运行物理内存可用仅 2.54 GB / 负载 84%），
   4.5% 的差值**不足以判定为真实劣势**，但也不宜声称已消除。
3. **窄残差流（§16）对短序列同样是净改进**：`smalln80` 在三个 T 上都更快，
   相对 `small` 提速 **5.3%（T=128）/ 24.3%（T=256）/ 26.9%（T=384）**。
   ⇒ 短序列劣势的缓解方向**已验证有效**：把 dim 从 128 压到 80、
   rank 提到 244（等栈参数），短序列劣势从 10.4% 收窄到 4.5%，且长一点的序列全面反超。
4. 加宽或调 batch 无法"补齐"：§16.5 已证层数对齐到 L=6 时同预算窄配置反慢 30–40%，
   §13.3 已排除"计算量/线程/算子改写"三条——**根因是算子数量**，
   所以有效的只有**减算子数**（融合、减层加宽）与**压激活宽度**（窄残差流）。

**结论**：

> 短序列倒挂**只在 batch=1 纯前向口径下成立**（交叉点 T≈384）。
> 在**训练态（batch=8）**，交叉点下移到 **T<256**：T=256/384 时 SunnyNet 已比 Transformer
> 快 1.5–2.4×。T=128 时仍慢 4.5–10.4%（其中 4.5% 落在测量噪声内）。
> **窄残差流把 T=128 的劣势收窄约 6 个百分点**，是已验证的缓解手段。

**局限**：3 轮取中位、内存负载 84%（绝对值应视为上界）、单一 batch=8、
未测 T=64/96 这类极短序列；"短句分类/对话回复"的真实形态（分类头/多轮拼接）
未构造实测，§19 只覆盖**语言建模的训练步开销**。

## 20. 极短序列与解码态：倒挂的真实边界

**触发**：批评称短序列倒挂"限制其在短句分类、对话回复中的应用"。§19 只测到 T=128，
且全部数据是**训练态或整段前向**。§20 补两个此前从未覆盖的口径：
**极短序列（T=32–96，常规短句的真实长度）** 与 解码态（逐 token 自回归）。

### 20.1 极短序列（训练态，`experiments/_shortseq2.py`）

新增窄配置 `smalln64`（d64 i128 r368 L4 = 367,508，+0.45%）。协议：batch=8、训练步、
每格独立子进程、3 轮交错取中位。

训练态 ms/token 中位与相对 Transformer 比值（>1 = 比 TF 慢）：

| 配置 | T=32 | T=64 | T=128 | T=192 | T=256 |
|---|---|---|---|---|---|
| `small`（d128） | 1.183 | 1.218 | 0.944 | 0.839 | 0.898 |
| `smalln80` | **0.907** | **0.940** | **0.730** | **0.549** | **0.557** |
| `smalln64` | **0.867** | **0.889** | **0.772** | **0.688** | **0.455** |

**读数**：

1. 训练态下窄配置在全部 T 上都不慢于 Transformer（比值 ≤0.94），
   T=32/64 时快 6–13%，T≥192 时快 1.4–2.2×。§19 的"T=128 仍慢 4.5%"针对旧 `d128` 配置
   ——`smalln64` 把 T=128 拉到 0.772（快 23%）。
2. **T=48/96 出现非单调**（T=96 慢于 T=128），与 T=32/64/128 的趋势矛盾。
   这是**单轮噪声**特征（本机内存占用 83%，绝对值属上界），**本表不引用这两点**，
   需更多轮重测才能定论；单轮数据不支持"全部 T 都已反超"。
3. 旧 `d128` 配置在 T=32 仍慢 18%（1.183），**窄化是有效手段**（同 §16/§19 结论）。

### 20.2 解码态（逐 token 自回归，`experiments/_decode_bench.py`）

**这是此前完全缺失的口径**。"对话回复"的真实部署形态是逐 token 解码，
而本仓库 Transformer 的 `forward_step` 原本是 `NotImplementedError` ⇒ **双方从未在此比过**。
为此实现标准 KV cache 推理路径（fp64 下单步/续算与整段前向 maxdiff **6.7e-16**，
新增 2 项不变量测试，测试总数 **52 → 54**）。

机制差异（决定解码态结论可能与训练态相反）：

- Transformer 解码：KV cache 省去重算 K/V，但每步 `q·k` 仍是 **O(t)**，单步访存随历史增长。
- SunnyNet 解码：状态 `(B,L,D)` **定长**，单步开销**与 t 无关**，恒 `O(1)`。

解码态 ms/step 中位（batch=1，3 轮）：

| 配置 | T=32 | T=64 | T=128 | T=256 | T=512 | T=1024 |
|---|---|---|---|---|---|---|
| `small` | 5.218 | 5.072 | 6.010 | 6.365 | 7.178 | 6.508 |
| `smalln80` | 7.861 | 4.469 | 5.664 | 7.509 | 6.406 | 5.247 |
| `transformer` | 4.164 | 3.533 | 4.180 | 3.512 | 4.091 | 4.872 |

**相对 Transformer 的比值（>1 = 比 TF 慢）**：

| 配置 | T=32 | T=64 | T=128 | T=256 | T=512 | T=1024 |
|---|---|---|---|---|---|---|
| `small` | 1.253 | 1.436 | 1.438 | 1.812 | 1.755 | 1.336 |
| `smalln80` | 1.888 | 1.265 | 1.355 | 2.138 | 1.566 | 1.077 |

**读数（§20.2 最重要的负面结论）**：

1. **解码态下 SunnyNet 全面慢于 Transformer（1.08–2.14×）**——与训练态结论**相反**
   （训练态 T≥128 时窄配置快 1.3–2.2×）。**同一个批评在两种口径下答案不同**，
   取决于"常规 NLP 任务"指的是训练/微调还是自回归解码。
2. **根因仍是每层算子数**（与 §13.3/§16.5 同源）：SunnyNet 单步要跑 L 层完整算子链
   （每层 30+ 算子），Transformer 每步 6 层但每层只有 qkv/attn/proj/mlp 几个大算子。
   状态虽定长省了 O(t) 项，但**常数项被算子调度开销吞掉**。
3. **`O(1)` 单步的理论优势在 T≤1024 内未兑现**：比值随 T 从 1.25 降到约 1.08–1.34，
   有收敛趋势（Transformer 的 O(t) 项在增长），但在 **T≤1024** 内仍未交叉。
   更长 T（≥2048）的曲线见 §20.3。
4. **T≤1024 的解码口径下 SunnyNet 是慢的一方**，不支持"SunnyNet 适合对话回复"。

### 20.3 局限

1. **batch=1、单条序列**：未测批处理解码（真实服务是 batch 推理，比值可能变化）。
2. 未做 KV cache 量化/分页：对比的是"朴素 KV cache vs 定长状态"，未含工程优化。
3. 双方都是 PyTorch 解释执行，未含手工 SIMD kernel；llama.cpp 这类手工 SIMD 实现
   不在 §20 范围（§21/§22 已单独做 AVX2 内核对照）。
4. 3 轮取中位，本机内存占用 83%，绝对值应视为上界。

**结论**：

> 短序列倒挂**取决于口径**。**训练态（batch=8）**：窄配置在 T=32–256 全程不慢于
> Transformer（快 6%–2.2×），§19 的"T=128 仍慢"只对旧 `d128` 成立。
> **解码态（batch=1，逐 token）**：SunnyNet **全面慢 1.08–2.14×**，与训练态结论相反；
> 其 `O(1)` 单步优势在 T≤1024 内**尚未兑现**，随 T 增大有收敛趋势但未交叉。
> ⇒ 若"常规 NLP 任务"指**训练/微调**，倒挂基本消除；若指**自回归解码**，倒挂真实存在。

## 21. 手写 AVX2 内核：编译链路打通与加速比实测

**目标**：在 CPU 上做手工 SIMD 内核，摆脱"快速推理依赖 GPU"的限制。

### 21.1 编译器复检

§13.4 曾按"本机无编译器"排除手写内核。复检结果：

| 项 | 此前记录 | 实测 |
|---|---|---|
| MSVC `cl.exe` | "存在但缺 SDK，不可用" | 确实存在（14.39.33519），仍缺 Windows SDK 头文件 |
| gcc / clang / zig | "全无" | 系统 PATH 里确实全无 |
| **w64devkit** | 未探测 | **已可安装**：GCC 16.2.0 + 自带 mingw-w64 头文件 |

`w64devkit` 是单文件自解压包，自带 libc 与全部头文件，不需要 Windows SDK，
也不需要 `reg.exe`（避开沙箱黑名单）。装于 `F:\devtools\w64devkit`（727MB）。

### 21.2 验证链（逐级，全部实测通过）

1. `gcc -O3 -mavx2 -mfma` 编译 AVX2 + FMA intrinsics 程序 → 运行正确。
2. `-shared` 编译 DLL → `ctypes` 加载 → 一阶递推 scan 数值 vs numpy **1.19e-07**。
3. 手写内核与 PyTorch autograd 对齐：前向 `2.38e-07`、`dp` `9.54e-07`、
   `dnu` **`0.000e+00`（逐位一致）**。已固化为不变量测试（测试总数 **54 → 55**）。

### 21.3 加速比（`experiments/_kernel_bench.py`）

内核：`sunnynet/kernels/scan_avx2.c`（**原创**；通道维 8 路 AVX2 并行、FMA 融合、
标量尾循环；反向含 `ds *= p_t` 时间传递项）。对照：torch `logspace_scan`。
**单线程对单线程**（内核单线程，故 `torch.set_num_threads(1)`）：

| B | T | N | AVX2 | torch | 加速比 |
|---|---|---|---|---|---|
| 8 | 256 | 160 | 0.154 ms | 3.397 ms | **22.03×** |
| 8 | 512 | 160 | 0.480 ms | 6.968 ms | **14.50×** |
| 8 | 1024 | 160 | 1.903 ms | 11.514 ms | 6.05× |
| 8 | 1024 | 512 | 9.010 ms | 88.610 ms | 9.83× |
| 8 | 2048 | 512 | 31.139 ms | 136.811 ms | 4.39× |
| 4 | 4096 | 512 | 35.130 ms | 151.688 ms | 4.32× |

**读数**：

1. **scan 算子级加速 4.3–22×**。torch 版走 `cumsum/exp` 物化中间张量；本内核单趟流过，
   无中间分配，且 FMA 把 `p*s + g` 合成一条指令。
2. **加速比随 T 增大而收窄**（22.0× → 4.3×）：内核时间随 T 线性，torch 版在长 T 上
   反而摊薄了调度开销。但即使 T=4096（超出本项目训练常用长度）仍有 **4.3×**。
3. **口径边界**：① 这是**算子级、单线程**口径；真实训练 torch 用 8 线程，
   加速比会收窄；② scan 只是训练步的一部分（§CPU 剖析：前向 24.8% / 反向 56.9%）。

### 21.3b 端到端 A/B（`experiments/_kernel_e2e.py`）

把内核接入 `SunnyBlock` 的 scan 调用点（`sunnynet/kernels/scan_auto.py`，
`autograd.Function` 包装 ctypes），其余完全不变。T=256、batch=8、8 线程、
smalln80、4 轮独立子进程交错：

| 轮次 | torch scan | AVX2 内核 |
|---|---|---|
| r1 | 268.66 ms | 279.55 ms |
| r2 | 281.18 ms | 280.14 ms |
| r3 | 394.52 ms | 353.98 ms |
| r4 | 314.24 ms | 289.48 ms |
| **中位** | **297.71 ms** | **284.81 ms** |

**读数**：

1. **正确性确认**：4 轮 **loss 全部为 7.589502，逐位一致** ⇒ 内核接入未改变训练语义。
2. **端到端加速比仅 1.045×，且落在噪声内**：轮间极差达 47%（268–394 ms），
   4 轮中内核 2/4 占优。**按测量纪律（§5/§16.4），此差异不足以判定为真实提升**。
3. **与算子级 6.05×（同 T）的落差符合预期**：scan 在 `logspace_scan` 内是热点，
   但在整训练步中占比有限，且 torch 版在 8 线程下已并行化了 `cumsum/exp` 部分。
   ⇒ "算子级快 N 倍"不能线性外推到整模型，两者必须分开陈述。

### 21.4 与 `torch.compile` 的关系（仍不可用，根因已查明）

本次发现 `torch.compile` 已能**走到** Inductor 的 C++ 编译步（此前根本进不去），
但卡在两处：
① Inductor 的 Windows 分支硬编码要求 MSVC 风格 CLI
（`subprocess.check_output(['where','cl'])` + `/I /O2 /MD /link`），
gcc 参数语法不被 `_is_msvc_cl`/`_is_clang` 接受；
② MSVC 链接路径依赖 `reg.exe`，被沙箱黑名单阻断。

**结论**：本机的自动融合路线（Inductor）需 clang-cl 才能走通，**尚未打通**；
但**手写内核路线已可用**——这不依赖 Inductor，只需 gcc，已验证。

- **尚未对标**：llama.cpp / ggml 未安装在本机，**没有直接测量**，
  因此没有数据支持"已超越"，也没有数据支持"做不到"。

  **T=4096 才反超（0.788，快 21%）**。
- ⇒ 工具链已打通，做顶尖 kernel 的**前置条件已满足**；
  与 llama.cpp 的对标**有待后续测量**，§21.5 不下结论。

## 22. 融合内核：竞争门控 + 门控概率 + 扫描单趟流过

**触发**：§21 只内核化了 scan 单算子，端到端仅 1.045× 且落在噪声内。本次把
`SunnyBlock` 里 scan **之前**的整段（组内成对竞争 → 门控概率 → 扫描）融成一个内核。

### 22.1 为什么能融

`SunnyBlock._pick_group` 在本项目**全部预设**下都返回 **8**（实测 dim 64/72/80/96/160/320/512/640/1024/1408），
恰好一个 AVX2 寄存器的宽度。于是 `_compete` 里的 `torch.roll(gg, -1/-2, dims=-1)`
退化为 **`_mm256_permutevar8x32_ps` 的 lane 置换**，组内竞争完全留在寄存器内。

torch 侧每层原本要物化的 (B,T,D) 级中间张量：2 个 `roll` + 2 个 `sub` + 2 个 `sigmoid`
+ `mul`（竞争），`sigmoid` + `sub`/`mul`（概率），再整条 `log`/`cumsum`/`exp`/`cumsum`
（扫描）。内核一趟算完，中间量不进显存。

**第二轮优化**：`sigmoid(g_i − g_j) = 1/(1 + e_j/e_i)`（`e = exp(−g)`），每 lane
**一次 `expf`** 替代原来的三次。

|---|---|---|

| 内核前向 `p` | 同上 | 7.51e-08 |
| 内核前向 `states` | 逐时刻递推 | 7.40e-08 |
| 内核反向 `dq` vs autograd | — | 1.94e-07 |

| 内核反向 `ds0` | — | 7.17e-06 |
| **接入模型后 loss** | torch 路径 | **0.000e+00（逐位一致）** |
| **接入模型后 59 个参数梯度** | torch 路径 | 最大绝对差 **4.60e-09** |

测试总数 **55 → 59**（新增：内核前向、内核反向、接入端到端、推理态等价性各 1 项）。

### 22.5 推理态：收益取决于线程口径与模型宽度

把单步融合内核（`sunnynet/kernels/step_avx2.c`：深度融合 + 深度可分卷积单步）
接入 `SunnyBlock.step`，数值等价确认（单步 vs 整段 **1.13e-06**）。

**第一轮测量（8 线程）结果全部不利**：

| 口径 | kernel/torch | 占优轮次 |
|---|---|---|
| T=128 B=1 8线程 | 0.736 | 0/4 |
| T=256 B=1 8线程 | 0.870 | 0/4 |
| T=512 B=1 8线程 | 0.810 | 0/4 |
| B=4/8/16/32 8线程 | 1.06–1.25 | 0/3 各 |

**根因（实测定位，三条）**：
1. **ctypes FFI 开销 13.6 µs/次**（含 `data_as` 取指针为 28.5 µs），
   而 torch 一个 3 算子链在 (1,80) 上只要 **7.2 µs**。解码 B=1 时每步 4 层 × 2 次内核
   = 8 次调用，**纯 FFI 就 0.1–0.2 ms**。
2. OpenMP 在小并行域上是负收益：并行域为 `(B, D/8)` 时线程唤醒约 **100 µs**
   （实测 B=1 时 131 µs vs 单线程 28 µs）。已用 `if(work >= 256)` 子句退回串行修正。
3. **更重要的口径发现**：解码态 B=1 时 **torch 1 线程比 8 线程快 1.42×**
   （2.71 vs 3.84 ms/step）。**此前所有解码测量都用 8 线程，口径本身次优**
   ⇒ 第一轮 A/B 的"全负"部分来自**用内核单线程去比 torch 的次优 8 线程配置**。

**第二轮：公平单线程口径 + 宽度扫描（`experiments/_decode_dim.py`，T=256 B=1）**：

| 配置 | dim | 3 轮 kernel/torch | 3 轮占优 | 5 轮 kernel/torch | 5 轮占优 |
|---|---|---|---|---|---|
| n80 | 80 | 0.907 | 2/3 | 0.938 | 4/5 |
| d160 | 160 | 0.929 | 3/3 | 0.986 | 2/5 |
| d320 | 320 | 0.939 | 3/3 | 0.952 | 4/5 |
| d512 | 512 | 1.035 | 0/3 | 0.983 | 3/5 |

**第三轮：加 delta 缓存后复测（`experiments/_decode_final.py`，5 轮，三指标并列）**：

| 配置 | dim | 中位比值 | 配对比值中位 | 占优 |
|---|---|---|---|---|
| n80 | 80 | 0.9421 | **0.9421**（一致） | 3/5 |
| d160 | 160 | 0.8342 | 0.9384（**矛盾**） | 3/5 |
| d320 | 320 | 0.9699 | 0.8789（**矛盾**） | 4/5 |

**收敛后的判断**：
1. **n80（实际使用的 dim=80）是唯一三指标一致的配置**：中位比值与配对比值都是 **0.9421**，
   即**有约 5.8% 的加速倾向**。但**符号检验仅 3/5 占优** ⇒ **未达显著门槛，不能判定提升**。
2. **d160/d320 三指标互相矛盾**（中位说快 16.6%/3%，配对说快 6%/12%，符号 3/5、4/5）
   ⇒ **落在噪声内**。
3. 第一轮"全负"的成因是线程口径不公平（内核 1 线程比 torch 的次优 8 线程配置），
   这一方法学修正成立且重要；但**改到公平口径后，收益仍不稳定**。
4. 根因未变：B=1 时张量 (1,D) 太小，融合省下的算子调度被 ctypes 跨界与张量分配吃掉。
   实测 ctypes 纯调用 0.28 µs（零参）/ 2.02 µs（8 参），torch 单算子 2.42 µs —— **同量级**，
   故融合必须靠"少调几次"而非"每次更快"。

**边界**：
- 上表是 **B=1 单线程**；生产解码多线程时需另测（本次未做）。
- **推理态内核收益不显著**，默认关闭（`SUNNY_KERNEL` 未设时关）；
  `set_kernel_active()` 可运行时切换，**建议只在训练态开启**。
- 推理态的**真正出路不在内核，在架构**：SunnyNet 单步 O(1)、Transformer 单步 O(t)，
  交叉点在 T≈2048–4096（§20.2，T=4096 时快 21%）。**长上下文解码才是兑现点**，
  短 T 的小张量解码本就不是优势场景。

**已顺带修掉的两处推理态开销**（数值等价、已验证）：
- `delta()` 单次 **57.2 µs**，4 层每步 229 µs（占解码步 8.3%）——纯 theta 的函数，
  已加版本号缓存（`delta_cached()`），theta 变更自动失效（实测 maxdiff 0.0）。
- `step_core/dw_step` 的 `contiguous().float()` 前置判掉，命中时不拷贝。

### 22.8 与主流框架/同行的差在哪里（内核化之后）

内核化不改变这层差距的成因，只改变自家绝对速度。 分三条说：

① 矩阵乘：已到顶，差距不在实现，在硬件。

- 训练步 `aten::mm` 占 **33.0%**（§22.4），走 MKL + oneDNN v3.12。
- §13.4 实测实际尺寸 GEMM **237.9 GFLOPS = 本机峰值约 80%** ⇒ **无实现层面空间**。
- **差距来源**：i7-8750H 只有 AVX2（无 AVX-512/VNNI/AMX），而 llama.cpp 面向的
  现代服务器 CPU 有 AVX-512 + VNNI，GPU 有 Tensor Core。**这是硬件差，不是代码差。**

② 元素级算子：内核化已把能砍的砍到接近上限。

融合内核把每层的竞争门控 + 门控概率 + 扫描融成单趟，算子数从 1124 → 704/步（§22.7）。
训练步提升 1.10–1.17×（§22.3/§22.6）。**剩余空间有限**：

- 反向占训练步 **88.7%**（§22.4），其中 `mm` 又占大头；元素级反向里
  `_log_softmax_backward_data` 8.6%、`mul` 7.3% 已属 MKL/oneDNN 覆盖范围。
- 继续融合的边际收益递减，且 §22.5 已证**推理态因张量太小无收益**。

③ 与同行的相对位置：内核化后未重测跨架构，不声称变化。

§16.3/§16.4 的对照（sunny80 vs rwkv/h3/mamba/hyena/linear_attn）**全部在
内核化之前测得**，本次**未重跑跨架构对照**。因此：

- 没有数据支持"内核化后超越了 rwkv"。
- **合理推断**（标注为推断，非实测）：内核化对 sunny80 有 1.10–1.17× 的训练步加速；
  若同行未做同等优化，相对位置会改善。**报告不对推断作结论。**
- 已知的确定差距（内核化无法消除）：
  - **短序列**：T<384 前向仍倒挂（§19/§20），根因是算子数量。
  - **长序列速度**：512<T<2048 领先，T=4096 时 Hyena 快 1.9×（§16）。
  - **收敛质量**：600 步早期样本效率与 H3 有差距（53.93 vs 56.8），未收敛不宜定论。

④ 与 llama.cpp / 主流框架的差距来源：硬件指令集差 + 未做同等深度优化的同行对比缺测，
不是"内核写不过"。内核这条链在本机已打通并验证到数值等价，**下一步的瓶颈是硬件与测量成本**。

### 22.10 推理出路的真正位置：单步解码成本随上下文的增长

§22.5 表明，在小张量（B=1、短 T）上做内核融合，收益被跨语言调用开销吃掉，
推理态内核默认关闭。推理的优势点不在内核，在架构：SunnyNet 单步解码是
**定长状态 O(1)**，Transformer 单步解码每步对全部历史做注意力，是 **O(t)**。

测法：每个 T 独立子进程，先逐 token 走满 T 步建立真实解码缓存（走满不计时，
避免 Transformer 被并行 prefill 加速），再测该上下文长度下的单步解码耗时；
1 线程（§22.5 已证解码态单线程优于 8 线程）；2 轮取中位。
脚本 `experiments/_decode_longpath.py`，数据 `experiments/results/_decode_longpath.json`。

| T | SunnyNet 单步 ms | Transformer 单步 ms | sunny/tf |
|---|---|---|---|
| 256 | 2.8716 | 2.4902 | 1.153 |
| 512 | 2.8818 | 3.0298 | **0.951** |
| 1024 | 2.8426 | 3.3265 | 0.855 |
| 2048 | 2.7269 | 4.7904 | 0.569 |
| 4096 | 2.9014 | 6.8544 | **0.423** |

**读数**：

1. **SunnyNet 单步成本平坦**：2.87 → 2.90 ms，相对 T=256 漂移在 ±5% 内
   （0.950–1.010），与"O(1)"一致。
2. **Transformer 单步成本随上下文单调上升**：2.49 → 6.85 ms（2.75×），
   与"O(t)"一致。
3. **交叉点 T≈512**：T=256 时 SunnyNet 慢 15.3%，T=512 起反超，T=4096 快 **2.36×**。
4. 与 §20.2 早期解码测量的差异来自口径：§20.2 用 8 线程并含最终 logits 开销，
   本次用 1 线程 + 定长单步，SunnyNet 的平坦性才显现。两者不可混用。

**结论（推理出路的定位）**：

- 短上下文（T<512）解码**不是优势场景**，且内核融合在此无收益（§22.5）——
  两条路都对短上下文无效，这是架构与执行开销共同决定的，不是实现问题。
- **长上下文解码是架构级兑现点**：交叉点 T≈512，T=4096 快 2.36×，且差距随 T 继续拉大
  （Transformer 单步 ∝t 无上界，SunnyNet 恒定）。这是不需要任何内核就能拿到的优势。
- 该结论的边界：**单条序列、B=1、随机初始化模型、2 轮中位**。真实服务是批处理解码，
  比值会变（batch 增大后 Transformer 的单步注意力可并行摊薄，优势会收窄），
  未测批处理口径。也不含 KV cache 量化/分页等工程优化（§20.3）。
- **本节的比较对象只有 Transformer**。解码态若与同样 O(1) 的 O(N) 同行同场对比，
  SunnyNet 在同一 torch 实现下并不领先（§23.3 实测：rwkv 全程第 2，比 `sunny`(torch)
  快 1.73–2.16×）；换整模型 C 后端则全长度第 1。「推理优势」成立的范围是
  "相较于 Transformer"，torch 路径不含同行。

**读数**：

1. **Transformer 的 O(t) 被复现**：2.473 → 6.962 ms（T 增 16 倍，单步成本增 2.82×）；
   对整模型 C 后端 T=4096 慢 **4.23×**。与 §22.10（2.36×）同向，本次比值更大是因为
   C 后端的基准比 §22.10 的 torch 单步更低。
2. **整模型 C 后端单步成本平坦**：1.560 → 1.647 ms，相对 T=256 漂移 −3%~+6%，
   全长度第 1。这与 §22.10 的 ±5% 一致。
3. **同一 torch 实现下 SunnyNet 打不平 rwkv**：`sunny`(torch) 全程 7/7/5/6/4，
   rwkv 在全部 5 个长度为第 2，比 `sunny`(torch) 快 **1.73–2.16×**。其 wkv 递推是
   纯逐元素 `p*s+k*v`，无 scan、无 log/exp 链。
4. **整模型 C 后端把次序反转**：`sunnyC` 在全部 5 个长度为第 1，比 rwkv 快
   **1.02–1.15×**。这一反转来自消除每步约 1100 次 aten 调用（§24.7），
   **不是架构算子数的改变**——两条路径必须分开陈述。
5. **hyena 的 FFT 长卷积在解码态不划算**：它的整段前向是七架构最快（§10.6），
   解码态却排第 8/第 6；逐 token 重建 FFT 的常数因子远高于其扫描类同行。

**结论**：

- **解码优势来自两条不同来源，不可混算**。同一 torch 实现下，SunnyNet 比 Transformer
  快（且越长越明显）但比 rwkv 慢 1.73–2.16×；换成整模型 C 后端，单步降到
  1.52–1.65 ms、全长度第 1，比 rwkv 快 1.02–1.15×。§22.10 的"推理优势"只在
  "对标 Transformer"这一比较下成立，且不覆盖 rwkv 这一列。
- **rwkv 在 torch 路径上仍是解码态最需要追的对手**。其优势来源是**算子数少**——
  单步只有 `p*s+k*v` 一条逐元素链，而 SunnyNet 单步含竞争门控（3 次 sigmoid）、
  门控概率、扫描、`W_c`/`W_s` 反馈，逐元素算子数量是它的数倍。
  这与训练态"瓶颈是算子数量而非 FLOPs"（§13.3/§16.5）是同一个根因；C 后端之所以
  反超，正是因为它把这一串算子收进一次 `sn_step` 调用。
- 边界：B=1、随机初始化、2 轮中位、未含批处理解码与 KV cache 量化/分页。
  `sunnyC` 与其它七条不是同一实现层级（C 内核 vs PyTorch），跨这一列比较时须标注。

### 23.4 差距的根因归并

十个维度里，SunnyNet 落后或仅持平的有：解码速度（同一 torch 实现下落后 rwkv）、
前向速度（落后 hyena）、L=6 训练速度（落后 30–40%）、100M 质量（落后 rwkv 3.6%）、
1.4M 质量（落后 h3 7.2%）、自然语言长距离检索（无优势）。
这些**收敛到同一个根因**：**逐元素算子数量**。

| 证据 | 数字 |
|---|---|
| 单块前向热点以 `mm`/`mul`/`add`/`var`/`cat` 为主，无单一支配算子 | §13.3 |
| 训练步 4524 次 aten 调用/步 | §22.4 |
| 减层加宽（等栈参数）训练快 12–17%、ppl −10.9% | §14.3 |
| 层数对齐到 L=6 后同预算窄配置反慢 30–40% | §16.5 |
| 解码态 rwkv 靠 `p*s+k*v` 单链取胜 | §23.3 |

So 解法方向只有一个：**减算子数**，不是加宽、调 batch 或换矩阵库。

### 23.5 逐维度攻克路线（可达性与硬约束）

| 维度 | 目标 | 可行动作 | 预期与约束 |
|---|---|---|---|
| **解码速度** | 追 rwkv | 融合 step 内核已实现（§22.5），但 B=1 下 FFI 吃掉收益；改**消除 FFI**（C 扩展/自定义 torch operator）后单步可少 10+ 次 aten 调用 | 可达，但需绕开 ctypes；上限是赶上 rwkv 而非超越 |
| **前向速度** | 追 hyena | hyena 的 FFT 常数因子极低，SunnyNet 的逐元素扫描难以在 batch=1 前向追上 | **受架构限制**：短前向是扫描类架构的结构性劣势 |
| **训练速度** | 层数对齐后仍持平 | 减层加宽已做（§14.3）；下一步是**算子级融合**（把 `W_c`/`W_s`/`_emit` 也并入内核） | 可达，但边际递减（融合上界 §14.7 仅 8.8%） |
| **质量 1.4M** | 超 h3 | h3 的差距（7.2%）在 600 步单种子噪声内；需多种子 + 更长步数才能判定 | 数据不足，不是架构劣势 |
| **质量 100M** | 超 rwkv | 落后 3.6%，且 lr 未逐架构调优 | 需 lr 搜索后重测，方向未定 |
| **自然语言长距离** | 超过 TF | 状态 `H_max=8192` 只保证"不被遗忘"，不保证"可检索"；需改状态设计 | **需架构改动**，非调参可及 |
| **批处理解码** | 未测 | batch 增大后 Transformer 单步注意力可并行摊薄，SunnyNet 优势收窄 | 必测，否则 §23.3 不完整 |
| **与 llama.cpp 直接对标** | 未做 | llama.cpp 有手写 SIMD kernel，本机已有 w64devkit 可编译对照 | 可达，但需另建 GGUF 侧实现 |

**硬约束（本机不可逾越）**：

- 硬件只到 AVX2（i7-8750H，无 AVX-512/VNNI/AMX），量化在本机是负优化
  （bf16 慢 520×）、低精度也无原生支持（§CPU headroom）。
- GPU 侧无 nvcc/CUDA toolkit/triton，无法编译 CUDA kernel（§15.5）。
- 0.5B 在 CPU fp32 不可实例化（§15.3）。

⇒ 以上路线里，**能落地的是"减算子数"这一条**，其余受硬件或架构结构性限制。
在这一条上能拿到的量级是**训练步 1.10–1.17×**（已到手）+
解码态若消除 FFI 的额外收益（未测）——**不足以"全面超越"六家**。

## 24. 通用递推 C Runtime

独立于 PyTorch 的 C 推理内核，目录 `sunnynet/runtime/`，只依赖 ctypes 与 C 编译器。

> 口径：本章 §24.12 起的 Mamba-2 / DeltaNet / GLA / HGRN2 实测数据是**历史记录**。
> 2026-10-26 起对外支持列表收敛为 RWKV-7 与 Mamba-2 两个架构，GLA / DeltaNet / HGRN2
> 的代码与 CLI 分派已移除（三者权重 ≥1.37 GB，C 化收益已贴带宽墙）。本章数据保留，
> 作为架构取舍的依据与可复现证据。

### 24.1 统一递推形式

```
s_t = a_t * s_{t-1} + b_t            逐通道独立           (SN_FMA)
s_t = a_t * s_{t-1} + (1 - a_t) * u_t 门控形式             (SN_GATED)
```

任何一阶线性状态递推都是这两种形式之一。求解该形式的架构在参数化上各异，
递推算子本身相同。内核按通道向量化（AVX2/FMA），T 维串行；`B` 维 OpenMP 并行。

### 24.2 跨架构映射验证

各架构递推手工映射到内核参数，与自身 PyTorch 递推逐元素比对。

| Mamba / S6 SSM | `a=decay`, `u=bu` (GATED) | 2.4e-07 |
| H3 对角 SSM | `a=decay`, `u=v` (GATED) | 1.2e-07 |

| 模式 | \|s\| 1/8 处 | \|s\| 末 | 漂移 | 单次量化相对误差 |
|---|---|---|---|---|

| 无界累加 | 466.8 | 3708.7 | 7.94× | 3.9e-03 |

| 模式 | \|s\| 末 | 溢出通道 | 溢出比 | 相对误差 |
|---|---|---|---|---|

| 8 | 256 | 4.3067 | 4.8008 | 0.897× |
| 8 | 1024 | 4.1083 | 3.8295 | 1.073× |

四个格 1.023 / 1.072 / 0.897 / 1.073，**方向不一致**（8 线程 T=256 反慢 10.3%）。
⇒ 不得声称端到端解码加速；与 §22.5 的推理态结论一致。

原因：内核沿 N 向量化、T 串行，模型侧 T、B 维度极小（T=1、B=1），
跨语言调用与状态搬运成本与单算子同量级（§22.5 实测 ctypes 空参 0.28µs、
8 参 2.02µs 对 torch 单算子 2.42µs）。内核的 9.90× 收益来自消掉块间串行依赖与
`exp(-P)` 中间张量，这在**跨段长序列扫描**里成立，在 B=1 单步解码里不成立。

B=1 单序列也不是 Runtime 的目标场景（§23.3：同一 torch 实现下解码态最优是 rwkv）。

### 24.7 整模型 C 解码：把整个前向搬进 C

§24.6 的负面结果定位在"跨语言调用 + 状态搬运"，那么出路是让每步只跨一次语言边界：
把嵌入查表、逐层 norm / 深度卷积历史 / 门控竞争 / 状态递推 / 读出、终态归一、LM head
全部放进 C，一步一次 `sn_step` 调用。权重由 `experiments/_export_runtime.py` 导出为打包
fp32 blob：矩阵乘权重预转置 `(in, out)` 配合 GEMV（一次 AVX2 load 覆盖 8 个输出行），
`circ ∘ W_s` 折成单矩阵，`p` 的 clamp 在构造期判掉（与 §16 一致）。

数值一致性 `experiments/_runtime_model_equiv.py`（1.4M ckpt，48 token 逐步）：

| 口径 | 结果 |
|---|---|
| 单步 logits max\|diff\| | 1.24e-05 |
| argmax 一致 | 48 / 48 |
| prefill 末 token vs torch 整段前向 | 3.81e-06 |

端到端延迟 `experiments/_runtime_decode.py`（B=1 单序列、单线程、每格独立子进程、
先走满 prefill 再测单步、3 轮交错）：

| prefill T | torch ms/step | C ms/step | 比值 | 逐轮占优 |
|---|---|---|---|---|
| 256 | 3.796 | 2.487 | 1.53× | 3/3 |
| 1024 | 3.802 | 1.851 | 2.05× | 3/3 |
| 2048 | 4.309 | 2.189 | 1.97× | 3/3 |

中位比值与逐轮符号检验一致（三格全 3/3），可判定真实提升。提速来源是消灭每步约
1100 次 aten 调用（剖析：`aten::mm` 16.4% / `aten::mul` 10.2% / `aten::select` 8.5% /
`aten::cat` 8.0%），不是算子融合本身。

**边界**：单线程 B=1 口径。CLI 默认 8 线程时 C 4.40 vs torch 4.56 ms/tok（24 token
单次读数，未多轮），差距被调度摊平——B=1 小张量并行是负收益（§20.2）。C 后端的优势在
单线程与更大批量，多线程 B=1 不得按上表线性外推。

**开发中定位到的一个真实 bug（已修）**：mingw 的 `fopen` 走 ANSI 代码页，含中文的
Windows 路径打不开权重文件；C 侧改用 `_wfopen` + `MultiByteToWideChar(CP_UTF8)`。

### 24.7b 整模型 C 解码的访存重构

`p100mw`（105.36M 参数，fp32 blob 467.6 MB）在 C 后端单步 80.2 ms，与 20M 级模型
（§24.7 的 1.4M ckpt 约 2 ms/step）不在一个量级。定位下来不在算子，在**权重布局**。

**先量访存上限**。单步解码至少要读一遍全部权重，因此耗时下界是
`blob 字节数 / 可达带宽`。写 `experiments/bench_bw.c` 用 AVX2 顺序读 419 MB
（纯读、不写、取 5 轮最优）：

| 线程 | 顺序读带宽 |
|---|---|
| 1 | 15.70 GB/s |
| 2 | 21.57 GB/s |
| 4 | 23.46 GB/s |
| 8 | 25.31 GB/s |

同期 `experiments/_bench_runtime_bandwidth.py` 量到 C runtime 单步 75.75 ms，
有效带宽只有 **6.17 GB/s** —— 是单线程下界的 1.08×、多线程下界的 1/4。
（注意：numpy 的 `a.sum()` 只量到 6.69 GB/s，会低估本机带宽，是早期误判的来源；
该脚本里的带宽对照因此只作量级参考。）

**原因是访问模式**。原实现的 GEMV 沿输出通道分块，内层遍历 `in` 时按 `out` 步长跨读：

```c
for (; j + 8 <= out; j += 8) {
    const float* row = Wt + j;
    for (int i = 0; i < in; ++i)
        acc = _mm256_fmadd_ps(b, _mm256_loadu_ps(row + (size_t)i * out), acc);
}
```

`experiments/bench_gemv.c` 对三种实现做微基准（p100mw 的 head `D→vocab`，46.1 MB）：

| 实现 | 1 线程 | 4 线程 | 8 线程 | 对原实现 |
|---|---|---|---|---|
| 原 stride 布局 | 4.11 GB/s | 8.66 | 8.39 | 1.00× |
| 原 stride + OpenMP | — | — | — | 2.11× |
| **行主序 `(out,in)`** | 18.91 | 30.91 | 28.86 | **4.61×**（1 线程）／**7.53×**（4 线程） |

行主序让每个输出行的权重连续，一次 load 命中相邻缓存行；并行沿输出通道切分，
各行无依赖。**只加 OpenMP 不改布局只有 2.1×，改布局才是主项。**

**改法与兼容性**。不动导出格式（仍是 `(in,out)`，已发布的 blob 无需重导）：
`sn_load` 读入后在内存里就地翻转成行主序，元素数不变因此后续区段偏移不受影响。
GEMV 改成按输出通道并行的连续读。

**线程数取物理核，不是逻辑核**。解码是访存受限，超线程不增加带宽；
实测 6 物理核 26.69 ms vs 12 逻辑核 36.05 ms（差 26%）。C 侧新增
`sn_recommended_threads()`：Windows 走 `GetLogicalProcessorInformation` 统计
`RelationProcessorCore`，Linux 解析 `/proc/cpuinfo` 的 `(physical id, core id)` 去重。

**最优线程数由权重规模决定，不是固定值**。同一台机上按 blob 档位扫线程
（`experiments/_decode_cthreads_size.py`，每档独立进程）：

![解码线程策略](../figures/perf_threads.png)

权重 ≤23 MB（d80–d256）时**单线程最优**：此时权重可驻留缓存，并行只会引入同步开销
（d128 单线程 1.70 ms，4 线程 2.96 ms）。权重 ≥39 MB（d384 起）越过缓存容量、
转为访存受限，**物理核最优**（d768 单线程 9.84 ms，6 线程 7.65 ms）。
分界在 32 MB 附近，故 `threads_for_blob()` 按 blob 字节数选择，而非一律取核数。

**A/B 对照**（`experiments/_ab_runtime_opt.py`：优化前的库由 `git show` 出源码单独编译，
同一 blob、同一 32 token 序列、5 轮交错 head-to-head）：

| 口径 | 结果 |
|---|---|
| logits max\|diff\| | **2.766e-05** |
| argmax 一致 | **32 / 32** |
| 逐位相同 | False（并行求和顺序改变舍入，符合预期） |
| 优化前 | 76.60 ms/token，6.10 GB/s |
| 优化后 | **25.72 ms/token，18.18 GB/s** |
| 加速 | **2.98×**，逐轮 **5/5** 占优 |

对 torch 的数值一致性仍满足既有容差（`_verify_runtime_opt.py` 用
`forward_step` 单线程口径：max\|diff\| 7.15e-06、argmax 32/32）。
线程数扫描（`experiments/_bench_runtime_threads.py`，5 轮中位）：

| 线程 | 1 | 2 | 3 | 4 | 6 | 8 | 12 |
|---|---|---|---|---|---|---|---|
| ms/token | 56.12 | 40.37 | 32.57 | 30.35 | **26.69** | 36.05 | 36.03 |

**边界**：2.98× 是**本机（i7-8750H 双通道 DDR4-2667）**的单步解码倍数，
只说明该实现的访存效率从 6.1 提到 18.2 GB/s。18.18 GB/s 仍低于
`bench_bw.c` 的 25.31 GB/s 上限，差额来自每步还有 reduce/归一化等非流式访问。
不得据此外推训练或 prefill（prefill 走同一 `sn_step` 循环，无批量并行）。
原实现 75.75→76.60 的差异来自测量脚本不同（前者含 `_load` 首次调用），不作陈述。

### 24.7c 权重存 fp16：把每步读取字节减半

§24.7b 之后单步仍是访存受限：`bench_layer.c` 里纯 GEMV 循环（41 次调用、无串行段）
在 6 线程下 14.67 ms（31.87 GB/s），而会话语境 21.6 ms —— 相邻调用间有状态依赖，
`gemv` 各自建 parallel 区，热力分散。既然内核已达纯顺序读上限，剩下的杠杆只有一个：
**每步少读字节**。

把 5 个 GEMV 矩阵与 LM head 在载入时截断成 fp16，小参数（layernorm 的 g/c、conv 抽头、
delta、标量、embed）保持 fp32：

| | fp32 | fp16 |
|---|---|---|
| 大矩阵权重 | 421.0 MB | 210.5 MB |
| 单步实读 | 467.6 MB | 约 222.3 MB |

内核 `gemv_h` 一次 `_mm256_loadu_si256` 读 16 个 half（32 B），拆成两个 `__m128i`
各经 `_mm256_cvtph_ps` 转 8 个 float 做 FMA —— 保持与 fp32 相同的 32 B 加载宽度。
`bench_f16b.c` 对比加载宽度（同一份 fp16 权重）：

| 线程 | fp32 | f16 128 位加载 | **f16 256 位加载** | 256 位/fp32 |
|---|---|---|---|---|
| 1 | 24.36 | 17.45 | **15.06** | 1.62× |
| 2 | 19.66 | 11.43 | **12.81** | 1.53× |
| 4 | 15.24 | 10.77 | **9.99** | 1.53× |
| 8 | 15.36 | 9.88 | **9.08** | 1.69× |

128 位加载损失了加载宽度，单线程反而慢于 256 位；两种加载数值完全一致
（vs fp32 的 max\|diff\| 均为 1.805e-04），所以取 256 位。

**误差有界，但不是逐位一致**。`experiments/verify_h.c`（C 直连，同 blob 同序列）：

| 口径 | 结果 |
|---|---|
| logits max\|diff\| 最坏 | 4.181e-03 |
| 相对偏差 | 7.42e-04 |
| **argmax 一致** | **64 / 64** |
| 末态各层 state max\|diff\| | 1.226e-02 |

fp16 只有 10 位尾数，权重相对误差约 5e-4，因此 7e-4 的 logits 相对偏差是量级内的
必然结果。偏差随步数累积但保持在 argmax 之下（本序列 64/64）。

**A/B 对照**（`experiments/_ab_fp16.py`：同一进程、同一 blob、11 轮交错
head-to-head、6 物理核）：

| 口径 | fp32 | fp16 |
|---|---|---|
| 中位 ms/token | 24.67 | **18.60** |
| min ms/token | 22.20 | **17.26** |
| 有效带宽（按 fp32 等价字节） | 18.95 GB/s | 25.14 GB/s |
| **逐轮配对** | — | **11/11 全胜** |

加速 **1.33×**（min 口径 1.29×），逐轮配对差中位 6.07 ms 且全为正。

**fp16 不再是访存受限**。fp16 实读 222.3 MB，18.6 ms 只对应 **12.0 GB/s**，
远低于 fp32 的 19 GB/s —— 瓶颈转移到 `cvtph_ps` 转换与指令发射。线程缩放
（`experiments/_fp16_threads.py`）因此对两者都不敏感：

| 线程 | 2 | 3 | 4 | 6 | 8 | 12 |
|---|---|---|---|---|---|---|
| fp32 中位 ms | 38.68 | 31.17 | 25.75 | 26.24 | 27.39 | 27.25 |
| fp16 中位 ms | 28.48 | 23.98 | 21.36 | **19.95** | 20.71 | 20.60 |
| 加速 | 1.36× | 1.30× | 1.21× | 1.32× | 1.32× | 1.32× |

**用法**：`--backend c --half`（Python 侧 `SnModel(..., half=True)`）。
fp32 仍是默认，逐位不变。CLI 实测 `--half` 下 decode 20.96 ms/tok。

**边界**：① 1.33× 是本机单步小数，不得外推 prefill 或训练；
② 端到端低于算子级（`bench_f16b.c` 4 线程 1.53×）—— 与既有纪律一致，
算子级微基准优势会被端到端摊薄；③ 相对偏差 7.4e-04 会让长序列的 greedy
解码偶发分歧，本序列 64/64 只是样本；需要逐位复现时用 fp32；
④ 权重文件仍是 fp32 blob，fp16 只在载入时转换，磁盘占用不变
（要减小磁盘占用需另做导出，未做）。

### 24.9 GGUF 只读与外部权重（RWKV-7）

`--gguf` 路径读入外部 GGUF 权重并逐 token 生成，不经 PyTorch。首个打通的是官方
RWKV-7 191M（BlinkDL/rwkv-7-world 的 `.pth` 经 llama.cpp 转 GGUF，bf16）。
张量命名与递推形式取自 llama.cpp 的 `src/models/rwkv7*.cpp`；参考数学取自
BlinkDL/RWKV-LM 的 `RWKV-v7/rwkv_v7_numpy.py`。

**（1）权重对齐**（`experiments/_gguf_align.py`）
GGUF 反量化结果与官方 `.pth` 逐张量比对，全部 `max|diff| = 0`（bf16 无损还原）。
LoRA 分解矩阵（w1/w2、a1/a2、g1/g2、v1/v2）在 GGUF 里存为 `(out, in)`，与 `.pth`
相反，其余矩阵同向。词表以 `\xNN` 转义字面量存字符串，需反转义为字节。

**（2）数值等价**（`experiments/_rwkv7_gguf_equiv.py`）
GGUF 驱动的实现与官方 `.pth` 的独立参考实现，逐 token 单步 logits 比对：

| 口径 | 结果 |
|---|---|
| 单步 logits max\|diff\| | 4.79e-06 |
| argmax 一致 | 12 / 12 |

**（3）生成**（`experiments/_rwkv7_gguf_bench.py`，温度 0.7 / top-k 20 / seed 42）
英文事实续写、中文续写、Python 代码补全均通顺：

```
The Eiffel Tower is located in the city of
-> Paris, France. The Eiffel Tower was designed by Gustave Eiffel in 1887 as a monument to
def fibonacci(n):
-> \n    if n < 2:\n        return n\n    return fibonacci(n - 1) + fibonacci(n - 2)
```

**（4）必须记录的两条边界**
- `rwkv7.py` 是 **numpy 参考路径**，不是 C 内核。它证明"Runtime 能读外部 GGUF 并算对"，
  解码约 388 ms/step——**这个数字不作速度成果陈述**。
- RWKV-7 的状态是**逐 head 的矩阵** `S ∈ R^{64×64}`，更新为
  `S_t = S_{t-1}⊙w_t − (S_{t-1}k_t)k_tᵀ + v_t k_tᵀ`，含 rank-1 去除项，
  **不是**元素级 `s = a⊙s + b`（24.1 的两种形式）。统一 IR 要覆盖它，需在元素级之外
  补矩阵值递推（外积 / rank-1 校正）层级。这是一条对既有"两种形式统一"叙事的修正。

**（5）开发中定位的 bug**
- rank-1 去除项必须用**未衰减**的 `S`：`S⊙w − (S k)kᵀ + v kᵀ` 里两项共用同一个 `S`。
  写成先衰减再算去除项，会在 step0（S=0）逐位正确、step1 起偏差 0.5+，极易漏过。
- LoRA 分解方向：`x @ W1 @ W2`，不是 `W1 @ W2 @ x`。

### 24.10 RWKV-7 的整模型 C 内核

§24.9 的 numpy 路径只用于验证权重正确性，解码约 388 ms/step。本节的把 RWKV-7 的
**整个单步前向**搬进 C（`sunnynet/runtime/rwkv7.c`，A 步一次调用）：嵌入查表、
逐层 norm、time-mix（`r/k/v/o` 投影 + `w/a/v/g` 四组 LoRA + `tanh`/`sigmoid`）、
逐 head 矩阵状态递推（含 rank-1 校正）、group-norm、`r_k` 项、channel-mix、
终态归一、LM head。权重由 `experiments/_export_rwkv7.py` 从 GGUF 导出为打包 fp32
blob（矩阵存 `(in, out)` 配合 GEMV；各层 v-LoRA 秩不同，逐层在头部记秩表）。

**（1）数值一致性**（`experiments/_rwkv7_c_equiv.py`，与 `rwkv7.py` 的 numpy 参考逐步比对）

| 口径 | 结果 |
|---|---|
| 单步 logits max\|diff\| | 7.25e-05 |
| argmax 一致 | 12 / 12 |
| 120 步长程 argmax 一致 | 120 / 120 |

**（2）解码速度**（`experiments/_rwkv7_c_bench.py`，单序列、已建状态后单步、
每格独立子进程、5 轮交错、60 步取中位）

| 实现 | ms/step | 相对 numpy | 逐轮占优 |
|---|---|---|---|
| numpy 参考 | 366.36 | 1.00× | — |
| C 内核 1 线程 | 67.92 | 5.39× | 5/5 |
| C 内核 4 线程 | 52.26 | 7.01× | 5/5 |
| C 内核 8 线程 | 48.88 | 7.49× | 5/5 |

C 内核 8 线程对 1 线程再快 1.39×（5/5）。**边界**：单线程单格绝对耗时方差大
（50–84 ms），随机器负载浮动，比值与逐轮符号检验方向一致；只测单序列单线程口径，
未测批量。GEMV 的列分块并行不改每列求和顺序，8 线程与 1 线程逐位一致。

**（3）开发中定位的 bug**
- 权重布局与 C 侧不一致：导出器判 LoRA 张量时用 `name.split(".")[-1]`，取到 `"weight"`
  而非模块名，导致 8 个 LoRA 矩阵未转置、`w1@w2` 维度塌成 `(64,64)`。逐张量 float
  计数对不上（差 21,120,000）时暴露。
- `w` 的 LoRA 中间夹 `tanh`（`exp(-σ(tanh(xw W1) W2 + w0)/√e)`），**不可折叠成单矩阵**；
  `a`/`v` 无夹层但为统一起见保留分解。

**（4）CLI**
`--gguf-backend c` 走 C 内核（`sunnynet/cli.py` `_main_gguf_c`），需先运行
`experiments/_export_rwkv7.py` 导出 blob。

### 24.11 INT4 权重量化

`sunnynet/runtime/quant.c`。分组对称 INT4：每 64 个连续权重共享一个 fp32 scale，
量化值域 [-8, 7]，两值一字节（字节 k 低半字节 = 组内第 k 个，高半字节 = 第 k+32 个）。
量化 GEMV 把激活也按同样分组量化到 INT8，用 `maddubs` 做点积：

```
Σᵢ (qᵢ − 8) xᵢ = Σᵢ qᵢ xᵢ − 8 Σᵢ xᵢ
```

权重保持无符号 [0,15] 直接进第一操作数，激活作有符号进第二操作数。
整模型 C 内核（`rwkv7.c`）按矩阵标志位混用 fp32 / INT4；向量与嵌入表保持 fp32
（嵌入是查表不是乘加）。

**（1）原语正确性**（`tests/test_quant_i4.py`）
量化 GEMV 的整数路径与显式整数求和**逐位一致**；反量化误差不超过该 block 的
`scale/2`；对 fp32 GEMV 的相对误差 ~0.11（4-bit 预期内）。

**（2）矩阵级速度**（`experiments/_quant_i4_bench.py`，单线程、每格独立子进程、3 轮中位）

| 矩阵 (out×in) | fp32 ms | INT4 ms | 加速 |
|---|---|---|---|
| 768×768 | 0.152 | 0.147 | 1.03× |

### 24.12 外部权重接入：Mamba-2 与 DeltaNet

`runtime/mamba2.py`、`runtime/deltanet.py`。同一 `step(token, state)` 接口加载另外两种
线性架构的官方权重，逐 token 单步递推，前向不经 PyTorch。权重体积大，不入库；
放到任意目录后用 `--hf-dir` 指向，或给测试设 `SUNNY_MAMBA2` / `SUNNY_DELTANET`
环境变量（不设则跳过相关用例）。

**（1）Mamba-2**（`state-spaces/mamba2-130m`，d_model 768 / 24 层 / 24 head × 64）

该 checkpoint 的 `config.json` 只有 `ssm_cfg: {"layer": "Mamba2"}`，**不含**维度超参，
须按 `mamba_ssm` 的 `Mamba2` 默认值补齐（`ngroups=1`、`d_state=128`），此组合与
`conv_dim = 1536 + 2·1·128 = 1792`、`nheads = 1536/64 = 24`、`A_log` 长度 24 三者自洽。
`vocab_size` 实际 pad 到 50288。权重 219 张量。

数学上每 head 状态是 `(head_dim=64, state_size=128)` 矩阵，但衰减 `dA = exp(dt·A)`
对 `(p, n)` 全同、外积也可分解，故退化为元素级一阶递推，无需矩阵-向量乘积：

```
dA  = exp(dt_h · A_h)
S_t = S_{t-1} ⊙ dA + (dt_h · B_g) ⊗ x_h
```

对照 `transformers` 的 `Mamba2ForCausalLM` 整段前向（`experiments/_mamba2_check.py`，
24 token）：

| 量 | 值 |
|---|---|
| max\|diff\| | 5.875e-04 |
| mean\|diff\| | 6.003e-05 |
| argmax 一致 | 24/24 |
| 单步 vs 分段续算 | **0.0**（逐位） |

5.9e-04 的量级需先排除公式错误：官方 **fp32** 自身相对 **fp64** 就偏离 **3.814e-04**
（`mamba2_chunk_scan` 的 cumsum/segment\_sum 路径），而本实现相对 fp64 只偏离
**2.518e-04**，**比官方 fp32 更接近真值**。⇒ 差异是单精度累积，不是数学错误。

贪心续写（GPT-NeoX tokenizer，须从 `EleutherAI/gpt-neox-20b` 另取——该 checkpoint
不含 tokenizer 文件）：

```

```

**（2）DeltaNet**（`fla-org` 的 DeltaNet 340M，hidden 1024 / 24 层 / 8 head × 128）

338 张量。`use_beta=true`（headwise，`b_proj` 输出 8）、`qk_norm=l2`、`qk_activation=silu`、
`use_short_conv=true`（q/k/v 各一路 kernel=4 深度卷积，无偏置）、`use_output_norm=true`
（无门控 RMSNorm，`o_norm` 长度 128）、`use_gate=false`、`allow_neg_eigval=false`
⇒ **无衰减门**，就是纯 delta rule。数学依据为 `fla/layers/delta_net.py` 的
`fused_recurrent` 路径与 `fla/ops/delta_rule/fused_recurrent.py`：

```
δ_t = (v_t − S_{t-1}ᵀ k_t) · β_t
S_t = S_{t-1} + k_t ⊗ δ_t
o_t = S_tᵀ q_t
```

`S` 在本仓按 `(k_dim, v_dim)` 存，是标准写法的转置，写代码时用
`kv = einsum("hkv,hk->hv", S, k)`、`o = einsum("hkv,hk->hv", S, q)`。

检查（`experiments/_deltanet_check.py`）：

|---|---|
| 秩 1 形式 vs 显式 `(I − β k kᵀ) S + β k vᵀ` | max\|diff\| **4.578e-05** |
| 全程 vs 分段续算 | **0.0**（逐位） |
| 重复运行 bit 稳定 | **0.0** |
| 贪心续写 | `<s>The capital of France is the city of Paris. It is the largest city in Europe and the second largest in the world.` |

**（3）速度**（`experiments/_hf_runtime_bench.py`，单线程 numpy 参考路径，
每格独立子进程 × 5 轮交错，30 步中位）

| 架构 | median ms/token | min | max |
|---|---|---|---|
| mamba2 | 45.68 | 38.27 | 55.42 |
| deltanet | 91.46 | 83.93 | 99.19 |

**这是参考路径的绝对耗时，不与任何基线比倍数。** 两者单步复杂度都是
`O(heads × head_dim × state_size)`，与上下文长度无关。

**（4）矩阵值递推层级已在 C 内核中实现**（`sn_mat_scan`，`runtime/recur.c`）：RWKV-7 与
DeltaNet 的状态更新都含 `S ← S + k ⊗ (·)` 这类外积累加，`SN_FMA` / `SN_GATED` 的
逐通道形式表达不了；Mamba-2 因衰减外积可分解而不需要。内核统一形式为

```
p[i]   = Σ_j S[i][j] · u[j]                    读更新前的 S
S[i][j] = S[i][j] · w[j] + v[i]·k[j] − p[i]·b[j]
y[i]   = Σ_j S[i][j] · r[j]
```

任一参数传 `NULL` 即跳过该项，覆盖四个架构：RWKV-7（`w`=衰减列、`u`=kk、`v`=v、`k`=k、
`b`=kk⊙a、`r`=r）、DeltaNet（`w=NULL`、`u=k`、`v=βv`、`k=k`、`b=βk`、`r=q`）。
逐 head 串行（head 间无依赖），沿 `C` 维 8 宽向量化 + 标量尾。

数值契约见 `tests/test_mat_scan.py`（11 用例：全项 / 无衰减 / 仅外积 / 纯衰减 / 无读出 /
`C ∈ {7,20,24,33}` 尾部路径 / 连续多步 / 拒绝非连续），相对误差 1e-7 量级（fp32 累加）。

**（7）开发中定位的坑**
- Mamba-2 的 `config.json` 缺 `state_size` / `n_groups`；`conv_dim` 只定出二者**乘积**
  （`(conv_dim − d_inner)/2 = 128`），单看权重无法拆分。`(8,16)` / `(1,128)` / `(2,64)` / `(4,32)`
  四种拆分与官方前向都吻合到同一量级，必须回到 `mamba_ssm` 默认值才能定案。
- DeltaNet 的 `head_k_dim == head_v_dim == 128`，显式矩阵形式乘错一侧**不会报维度错**，
  只会静默算成另一个式子（首轮检查因此得到 134.3 的假差异）。
- `state-spaces/mamba2-130m` 不含 tokenizer；用 Llama tokenizer（vocab 32000）喂
  50277 词表的模型会得到乱码，须另取 GPT-NeoX tokenizer（vocab 50254）。

**（8）DeltaNet C 内核开发中定位的五个真实缺陷**（逐层对表定位，非静态自检）

1. **`l2norm` 写成了逐 8 宽分块归一化**，应对整个 head（128 维）求一次范数。症状：
   `v`（不做 l2norm）逐位一致，`q`/`k` 差 0.09 / 0.99 —— 差异只出现在做了归一化的张量上。
2. **`dconv_silu` 原地调用时把 silu 后的值存进历史**。参考实现存的是卷积**输入**
   （`hist[-1] = x`，即 conv 前的投影值）；原地写回后 `x` 已是 silu 结果，`memcpy` 会存错。
   须留一个 `tmp` 缓冲先拷原始输入。**单步看不出来，历史全 0 时两种写法结果相同**——
   必须跑到第 4 步（conv=4）以上才会暴露。
3. **`o_norm` 要逐 head 归一化**，不是整段 1024 维一次归一；且 `o_proj` 的输入维是
   `NH·HV`，不是 `HV`。
4. **权重转置方向**。HF 存 `(out,in)`；若 C 侧 `gemv` 按 `(out,in)` 行主序、每行连续读，
   就**不需要转置**。第一版把 `gemv` 写成按 `(in,out)` 读，于是导出器转置了矩阵——
   方阵（1024×1024）转置后不报错、也不等于自身，只会静默算成别的式子。
   最终改为与 `sunnynet.c` 同一套 `(out,in)` + 按输出通道并行，导出器不再转置。
5. **tied 时 `head` 与 `embed` 都是 `(vocab,D)`**，正是 `gemv` 要的 `(out,in)` 布局；
   第一版额外做了一份转置，反而算错。三个 tie 场景（`tied_head=1`）须与 HF 的
   `lm_head` 语义对齐后再定布局。

**（12）GLA 开发中定位的真实缺陷**：单步 readout 差 **96%** 而各投影（`attn_norm` /
`q` / `k` / `v` / `exp(gk)` / `g_proj`）全部正确到 1e-7。根因是 `gla_scan` 里每个 head
都读了 `v` 的**第 0 段**（`v + j`）而非该 head 自己的 value 段（`v + h·HV + j`），
于是所有 head 共用同一 value 向量。

定位手段是**层内阶段探针** `sn_gla_probe`（暴露 10 个阶段的中间量：`attn_norm` / `q` /
`k` / `v` / `exp(gk)` / `g_proj` / readout / 逐 head RMSNorm 后 / 门后 / `o_proj`），
逐阶段与参考对表——**只看层输出定位不到**，因为层输出是多个正确项与一个错误项的和。

`head_k_dim ≠ head_v_dim`（128 vs 256）时这种索引错**不会报越界**：`v` 总量是
`NH·HV = 1024`，用 `h·HV` 与用 0 都在界内，只会静默算成别的式子。

定位手段：在 C 侧加 `sn_dn_dbg` 转储逐层中间量，与 numpy 参考**逐项**对表。
五处缺陷里有四处是纯数值错位（不崩、不报错），只能靠中间量比对揪出。

**（12）HGRN2 整模型进 C**（`runtime/hgrn2.c`，`fla-hub/hgrn2-1.3B-100B`）

dim 2048 / 24 层 / 16 head / head_f_dim = head_i_dim = 128 / vocab 32000 /
244 张量 / 1.36B 参数。该 checkpoint **不在 `transformers` 原生支持列表内**
（5.20.2 只有 mamba / mamba2 / rwkv / zamba / falcon_mamba），故对照基准是本仓
独立书写的 numpy 参考（`runtime/hgrn2.py`，显式循环矩阵-向量，不借 einsum）。

与 GLA 的递推同构（论文称 "identical recurrent structure"，HGRN2 复用 GLA 内核），
四处参数化差异：

| 项 | GLA | HGRN2 |
|---|---|---|
| key | `k_proj` 独立投影 | **无 k_proj**，`k = 1 − exp(g)` 由衰减导出 |
| decay | `gk_proj` 低秩 (16 维) + `logsigmoid` / normalizer | `f_proj` 满秩 2048 + `logaddexp(lb, log1p(−lb) + logsigmoid(f))` |
| 下界 | `clamp_min` 标量（本 checkpoint 未用） | **逐层学习 `lower_bounds[24, 2048]`** |
| q / 输出门 | q 直接读出；输出门 `RMSNorm(o)⊙silu(g_proj)` 逐 head | **q 过 silu**；**无输出门**，`o` 在 value 维整体 RMSNorm |

`lb` 在层循环里预算：`softmax(lower_bounds, dim=0).cumsum(0) − softmax(...)[0]`，
softmax 在**层维**（24）上做，第 0 层恒为 0；层内只有 `i > 0` 参与混合。

对照结果：

| 检查 | 结果 |
|---|---|
| 单步 vs 分段续算 | **0.000e+00**（逐位） |
| 单步 vs 独立 numpy 参考（12 token） | **1.192e-05** |
| C 内核 vs numpy 参考（逐 token，36 步） | max\|diff\| **3.552e-05**，相对 **2.384e-06** |
| argmax 一致 | **36/36** |
| 贪心续写 | `The capital of France is Paris.` |
| 全量测试 | **183 passed / 8 skipped / exit 0**（无回归，原 175 / 2） |

速度（`experiments/_hgrn2_c_bench.py`，B=1 单序列，numpy 侧预热 2 步后计 8 步中位）：

| 线程 | ms/tok | vs numpy |
|---|---|---|
| numpy 参考 | 262.44 | 1.00× |
| 1 | 382.00 | 0.69× |
| 4 | 221.42 | 1.19× |
| 8 | 203.33 | **1.29×** |

权重 5.46 GB fp32。单线程顺序读下限 `5.46 GB ÷ 18.63 GB/s ≈ 292.9 ms`，实测单线程
382 ms 顺着这条线（纯 GEMV 的单线程顺序读上限即 18.63 GB/s）；8 线程 203 ms 对应
26.8 GB/s，已贴近 4 线程测到的 30.45 GB/s 多线程上限。**这是「权重越大、C 化收益越小」
的极端一端**：5.46 GB 的权重任何实现都只能等内存读完，1.29× 即全部可得的余量。

两个开发中定位的真实缺陷：

- **blob 加载用 `fseek(f, 0, SEEK_END)` 探长度会静默失败**。mingw 的 `long` 是 32 位，
  5.46 GB > 2³¹ 时 `ftell` 溢出，`fseek` 返回非零，加载函数直接返回 NULL 而不报原因。
  该段代码在改用文件映射后本就多余，直接删除。
- **5.46 GB 的 fp32 blob 不能 `malloc` + `fread`**。本机物理内存 15.87 GB、空闲 5.79 GB，
  复制进堆要再占 5.46 GB，叠加导出期的峰值即段错误。改用 `MapViewOfFile` / `mmap`
  只读映射，由页缓存共享，只有真正读到的页占内存——**这对边缘端是必要条件而非优化**。

numpy 参考同样改走 blob 的 `np.memmap`（与 C 读同一份同布局数据，对照更严格），
HF 侧则逐张量惰性转换；两条路径都不再需要 5.46 GB 常驻。

**（13）HGRN2 的 INT4 权重路径**（`--int4` 导出 + 内核按标签分发 `sn_gemv_i4`）

上表的 1.29× 说明 fp32 的 HGRN2 已无余量可挖——**权重 5.46 GB 时任何实现都只能等内存读完**。
唯一剩下的杠杆是**减少读取字节**，故把 RWKV-7 上已验证的分组 INT4 GEMV（`runtime/quant.c`）
接到 HGRN2：GEMV 矩阵按 `block=64` 对称量化，每个矩阵前置一个 `int32` 格式标签
（1=INT4，0=fp32），blob magic 换成 `SHGQ`（`0x51474853`）。向量与嵌入表不量化
（嵌入是查表不是乘加）。**fp32 blob 与其验证链完全不动**，两种 blob 文件名与 magic 都不同。

| 项 | fp32 | INT4 | 比 |
|---|---|---|---|
| blob 体积 | 5457.6 MB | **993.4 MB** | **5.49×** |
| 单步 1 线程 | 382.00 ms | 158.82 ms | 2.41× |
| 单步 4 线程 | 221.42 ms | 88.42 ms | 2.50× |
| 单步 8 线程 | 203.33 ms | **72.19 ms** | **2.82×** |
| 理论下限（顺序读 18.63 GB/s） | 293.2 ms | 53.3 ms | — |

CLI 端到端（`--blob .../hgrn2.q4.bin`，backend 仍标 `hf/hgrn2/c`）：
`The capital of France is Paris.`，**79.86 ms/tok**（fp32 同 prompt 为 222.05 ms/tok，**2.78×**）。

**精度**：分组 INT4 取 `scale = amax / 7`（覆盖 `[0,15]` 共 7 个正向档，`q=0` 对应 −8），
理论相对误差 `1/(2·7) ≈ 0.071`，单矩阵实测 **0.097–0.168**（cos 0.993）——
与 RWKV-7 的 ~0.11 同级。整模型逐 token 相对误差中位 **0.242**（合成 token，36 步），
逐层探针显示 **layer 0 单步即 0.189、层间不放大**，故差异全部来自量化本身而非状态累积。

质量按**真实文本贪心续写**看（`_hgrn2_int4_quality.py`，与 RWKV-7 同口径）：

| prompt | fp32 | INT4 |
|---|---|---|
| The capital of France is | `Paris.` | `Paris.` |
| Water is made of hydrogen and | `oxygen.` | `oxygen.` |
| The theory of relativity was proposed by | `Albert Einstein in 1905.` | `Albert Einstein in 1915.` |
| The sun rises in the east and sets in the | `west.` | `west.` |

首词与语义全部保持，逐 token 一致率 4–9/20；退化表现为**重复倾向**（`Hydrogen is a very
light element.` → 后半开始循环）与**事实细节错**（1905→1915）。**不声称质量无损**——
4 bit 欲压质量须配校准，而敏感矩阵保 fp32 的尝试（`fproj+head` 保 fp32）实测无改善
（argmax 仍 20/36），说明误差是多矩阵分布式而非集中在某一类。

测试：`tests/test_hgrn2_c.py` 增 3 项（Q4 magic 加载、与 fp32 的有限/有差异/argmax 过半、
重复运行逐位稳定），全量 **186 passed / 8 skipped**（原 183 / 8，无回归）。

**（14）同一 INT4 机制推广到 GLA 与 DeltaNet**

§24.12 的表里 GLA 的 1.01× 与 DeltaNet 的 1.10× 比 HGRN2 更值得救：两者权重都是
1.37 GB fp32、**C 化收益已被带宽墙吃掉**，而 INT4 把理论下限从 73.5 ms 压到 14.4 ms。

| 架构 | blob fp32→INT4 | 8 线程 fp32→INT4 | 加速 | 相对误差中位 | argmax |
|---|---|---|---|---|---|
| HGRN2-1.3B | 5457.6 → 993.4 MB (5.49×) | 203.33 → 72.19 ms | **2.82×** | 0.242 | 20/36 |
| GLA-340M | 1366.8 → 305.8 MB (4.47×) | 66.54 → 33.83 ms | **1.97×** | 0.257 | 19/36 |
| DeltaNet-340M | 1366.4 → 306.7 MB (4.46×) | 70.91 → 35.30 ms | **2.01×** | 0.243 | 33/36 |

单步（state=0）相对误差：HGRN2 0.264 / GLA 0.264 / DeltaNet **0.047** —— DeltaNet 明显更低
（它的 `q/k/v/o` 是纯线性投影，误差不经过 `exp(g)` 放大），故 argmax 命中 33/36 也最高。

CLI 端到端（`--blob .../xxx.q4.bin`）：

```

DeltaNet : The capital of France is Paris. It is the largest city in the world...  [40.06 ms/tok]
HGRN2    : The capital of France is Paris.                [16 tok 79.86 ms/tok]
```

不量化的项：GLA 的 `gk_proj.1.weight`（`in = GR = 16` 不满足 block 64，导出器自动回落
fp32）；DeltaNet 的短卷积核 `q/k/v_conv1d`（是卷积不是 GEMV）与 `b_proj`（`out = NH = 8`，
体积可忽略）。嵌入表两处都不量化。

blob 协议照搬 HGRN2：新 magic（GLA `QLAG` 0x51414C47 / DeltaNet `QNDD` 0x51444E44），
每个 GEMV 矩阵前置 `int32` 标签。fp32 blob 与全部既有验证链不动。

测试：`tests/test_gla_c.py`、`tests/test_deltanet_c.py` 各增 2 项（Q4 加载与误差上界、
重复运行逐位稳定），全量 **190 passed / 8 skipped**（原 186 / 8，无回归）。

### 24.13 预编译原生库

前十二节的六个共享库（`runtime` / `model` / `rwkv7` / `quant` / `abi` / `kernels`，
§24.12 依次加入 DeltaNet / Mamba-2 / GLA / HGRN2 四个整模型库后为 **10 个**）
原本都在**首次调用时用本机 gcc 现编**，因此 `pip install` 之后仍需另装 C 编译器。
本节把编译挪到 **wheel 构建期**：构建机上编好、产物随包分发，装机后直接加载。

**产物布局**：`sunnynet/_prebuilt/<平台标签>/`，标签为 `win-x86_64`、`linux-x86_64`、
`macos-arm64` 等（`sunnynet/_native.py` 的 `platform_tag()`）。加载器按当前平台标签
查找；`locate()` 命中则直接 `CDLL`，未命中退回原有的源码编译路径——**对没有预编译
产物的平台行为不变**。

**指令集门槛**：库以 `-mavx2 -mfma -march=x86-64-v3` 编出，只有 x86-64 且支持
AVX2+FMA 的机器能执行，故判定按**指令集**而非仅按平台（`isa_ok()`）。不达标的机器
即使命中了产物也走源码编译，避免非法指令崩溃。

**六库加载器改造**：各自抽出 `_bind(lib)` 绑定 argtypes，`load_*` 开头插入预编译
短路，`*_available()` 同步放宽为「有编译器 **或** 有可用预编译库」。

实测（Windows / i7-8750H，全部真机执行）：

| 验证项 | 结果 |
|---|---|
| 预编译库 vs 源码编译库（`recur_scan` 同批输入） | out / send **max\|diff\| = 0.0，逐位相同** |
| 无 gcc（PATH 精简、无 `SUNNY_W64`）加载六库 | 全部成功，`CDLL` 路径指向 `_prebuilt/win-x86_64/` |
| 无 gcc + 源码树全量测试 | **115 passed / 21 skipped / exit 0** |
| 同上，改造前 | 89 passed / 47 skipped / exit 0 |
| 差值 26 的含义 | 原先因缺编译器**跳过**的用例现在真实执行 |
| 完全隔离（无源码树、无 gcc、`PYTHONPATH` 指向安装目录） | **106 passed / 30 skipped / exit 0** |
| 有 gcc + 源码树全量测试 | **126 passed / 10 skipped / exit 0**（无回归） |
| wheel 内预编译产物 | 11 个 `_prebuilt/` 条目（10 个 dll + `sources.sha256`），wheel 总 74 文件，标签 `py3-none-win_amd64` |

`SUNNY_NO_PREBUILT=1` 可强制关闭预编译短路，用于上表第一行的对照验证。

含二进制时 wheel 打平台标签（`py3-none-win_amd64`）而非 `py3-none-any`，避免把 A 平台
产物发给 B 平台；平台不匹配的机器由 pip 从 sdist 构建，源码路径完整可用。sdist 只由
单一平台产出，`_prebuilt/` 不入 sdist（只带 C 源码）。

**产物与源码的一致性检测**。开发态下改了 C 源码但不重编，加载器会静默命中旧的预编译
库——开发中真实发生过：`sn_mat_scan` 编译通过，Python 侧却报 `AttributeError`，
因为命中的是改动前的 `sunnynet_runtime.dll`。故 `build_prebuilt()` 额外写出
`_prebuilt/<标签>/sources.sha256`（按库分组的源码内容哈希），`locate()` 载入前比对。

判定用**内容哈希而非 mtime**：pip 解包会把源码 mtime 刷成解包时刻、恒新于产物，
按时间判会把装好的包一律判成过期。手动篡改清单中 `runtime/recur.c` 的哈希后，
`locate()` 六个库全部返回 `None`（回退源码编译）；恢复后重新命中。

开销：Windows 实时防护下进程内首次打开文件约 14–20 ms，之后约 0.4 ms；一次载入只
比对该库用到的 2–5 个源文件，故一次性约 70 ms，远小于源码编译的数秒。源码没随包
分发时无法判定，按不过期处理。契约测试 `tests/test_native_prebuilt.py`（5 项）。

隔离验证（无源码树、无 gcc、`PYTHONPATH` 指向安装目录）：

| 检查 | 结果 |
|---|---|
| 六个库 `locate()` | 全部命中 `_prebuilt/win-x86_64/` |
| `load_runtime()` 实际加载路径 | 指向安装目录下的 `sunnynet_runtime.dll` |
| `prebuilt_stale()`（含清单） | False——内容哈希一致，未误判过期 |
| 隔离环境调用 `mat_step` | max\|diff\| 1.43e-06（对 numpy 参考） |

**构建期的两个真实缺陷**（都在 Windows 上炸，Linux 不复现）：

一、`build_prebuilt()` 原先直接调各模块的 `_compile(gcc)`，写的是**共享的**
`<pkg>/_build/<dll>`。该文件一旦被本进程（或同一测试会话里先跑的其他用例）加载过，
Windows 不允许覆盖写，gcc 写不进去即报编译失败。此前全量测试顺序依赖地出现 3 个
`RuntimeError`，单独跑该文件却全过。修法：编译落到 `tempfile.TemporaryDirectory()`，
产物再复制到目标目录。新增回归用例——先 `model._load()` 令 dll 处于已加载态，再断言
七库全部写出。

二、`subprocess.run(..., text=True)` 按 UTF-8 解码子进程输出，Windows 下 gcc 的诊断
按**系统代码页**（简体中文为 GBK）输出，源码路径含非 ASCII 时解码即抛
`UnicodeDecodeError`——真实编译错误被异常自己盖掉。六处 `_compile` 里只有 `abi.py`
单独做了容错解码，其余五处没有。修法：统一走 `_native.run_cc()`，收 bytes 再
`decode("utf-8", errors="replace")`。

同源问题还有一处：`deltanet_c._recommended_threads()` 直接 `CDLL` 拼接
`_build/sunnynet_model.dll`，既绕过预编译库查找，也是上条缺陷的触发源；改为复用
`runtime.model.recommended_threads()`。产物目录下的 dll 若已被加载，复制同样被拒，
故 `build_prebuilt()` 对每个库单独捕获 `PermissionError`，被占用的库单列说明而不整体
失败。

三、`prebuilt_stale()` 的判定结果有进程内缓存，但 `build_prebuilt()` 重建后没清它——
「改源码 → 重建 → 加载」的正常开发流程会一直读到旧的过期结论，等于每次仍退回源码编译。
修法：重建末尾 `_STALE_CACHE.clear()`。

四、契约测试里硬编码产物名 `"sunnynet_runtime.dll"`。清单的键是带平台后缀的产物文件名，
Linux 下是 `sunnynet_runtime.so`，故 `man["sunnynet_runtime.dll"]` 直接 `KeyError`。
本机是 Windows 恰好匹配，本地一直全绿；CI 的 `architecture-selfcheck` 只在
`ubuntu-latest` 两个矩阵上红。修法：测试从模块取 `DLL.name`，不写字面量。
提交 `8a7bfa4` 的 CI 已因此失败。

五、**漏登记新架构库不会让任何测试变红**。`build_prebuilt()` 只按 `MODULES` 遍历；
新增的 `runtime/<arch>_c.py` 若忘了加进 `MODULES`，既不进 wheel、也不写清单，装机后
只能退回源码编译（需自带 C 编译器），而在装了编译器的开发机上完全看不出来。加入
`hgrn2_c` 后曾发现 `_prebuilt/win-x86_64/` 里少了 `sunnynet_hgrn2.dll`。修法：新增反向
覆盖用例，`runtime/` 下每个 `*_c.py` 都必须登记进 `MODULES`。

**契约测试**：`tests/test_native_prebuilt.py` 现 8 项，覆盖清单与源码一致、篡改哈希
判过期、无清单不误判、源码缺失不误判、已加载态下重建、重建后清缓存、每个模块都
提供 `_link_cmd` 与 `DLL`，以及反向覆盖（每个 `*_c.py` 都在 `MODULES` 里）。
用例名一律取自模块属性，跨平台可跑。

### 25.2 6GB 卡的配置边界

| 配置 | 结果 |
|---|---|
| bs=1 × 256 | 通过，1.220 ms/tok |
| **bs=2 × 256** | **通过，0.744 ms/tok（选为训练配置）** |
| bs=4 × 128 | 通过，0.818 ms/tok |
| bs=4 × 256 | 训练后期 OOM |
| bs=8 × 128 | 训练后期 OOM |

三条测量陷阱（均实测复现）：

1. **`expandable_segments` 在 sm_61 上不可用**。加
   `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 后 OOM 出现得更早，
   而非更晚。这与 §15 的记录一致。
2. **显存被其他进程占用时，free 数值不可信**。常驻 Ollama 占 383 MiB 时，
   名义 free 5649 MiB，但尝试分配 12 MiB 即失败；先 `keep_alive: 0` 卸载使
   free 回到 6031 MiB 后恢复正常。这是 WDDM 分配器碎片，不是算术问题。
3. **验证批次也吃显存**。`val-batches 8` 在 bs=2 下于验证阶段 OOM，
   降到 2 后全程稳定。训练配置与验证配置需分别定界。

### 25.3 权重打包与加载验证

`sunnynet-release`（`sunnynet/release.py`）一次导出三类资产 + 模型卡 + sha256 清单：

| 产物 | 大小 | sha256 前 12 位 |
|---|---|---|
| `sunnynet-p100mw.pt` | 467.7 MB | `399e604e635b` |
| `sunnynet-p100mw.safetensors` | 421.5 MB | `c7287c76ac8b` |
| `sunnynet-p100mw.runtime.bin` | 467.6 MB | `95c195e47637` |

safetensors 含 139 张量。**绑定嵌入（`tie_embeddings=True`）时 `head.weight` 与
`embed.weight` 共享存储，safetensors 会拒绝保存并报 "Some tensors share memory"**；
导出器摘掉 `head.weight` 并在 metadata 写 `sunnynet.tied_head=1`，加载方复用 embed 即可。

导出后另做一次头部规范化：safetensors 0.8.0 序列化多键 metadata 时顺序不稳，同一
checkpoint 连续导出会得到不同字节（数据段完全一致），发布 sha256 因此不可复现。导出器
按 `sort_keys` 重写头部 JSON 并更新长度字段，数据段不动。实测未规范化六次导出得到六个
哈希，规范化后六次全同。

三条加载路径实测（同一权重）：

| 路径 | 输出 | 速度 |
|---|---|---|
| torch 后端 | `"“H不得你，也不可不得…"` | 143.6 ms/tok |
| C Runtime（`.runtime.bin`） | `"「尚與子之子，雖以一名，於我也。"` | **80.2 ms/tok** |
| OpenAI 服务（官方 SDK） | 四种调用方式全通过 | — |

C 后端对 torch 后端的读数是单次（20 token），**不作加速比陈述**，只证明导出的
blob 布局与内核期望一致、可独立于 PyTorch 加载。

### 25.4 Agent 生态接入：Ollama 的三个坑

RWKV-7 191M GGUF 经 Ollama 真实导入并生成成功（`family=rwkv7`、
`parameter_size=191.13M`、`runner=llamacpp`、`tokenizer.ggml.model=rwkv`）。

1. **必须显式写 TEMPLATE**。Ollama 内置 `rwkv-world` 模板会在 prompt 外再包一层
   `User: / Assistant:`，同一 prompt 下输出退化为复读
   （`"-of-the-world-of-the-world-of-..."`）。写入
   `TEMPLATE """User: {{ .Prompt }}\n\nAssistant:"""` 后输出恢复
   `" The capital of France is Paris."`，且与自家 C runtime 的 raw 输出**逐字一致**
   ——证明问题在模板而非分词。
2. **`Error: could not locate ollama app` 的真实含义是 server 未运行**。
   `ollama create` 在 server 离线时会静默尝试拉起本地 app 并失败。已精确复现：
   `OLLAMA_HOST` 指向空端口 → 该错；server 在线 → 正常。诊断脚本须先探活
   `GET /api/version`，否则会把环境问题误判为安装损坏。
3. **`OLLAMA_MODELS` 必须与 server 侧一致**。只设 `OLLAMA_HOST` 时 `create`
   会把 blob 写进默认目录，与运行中的 server 目录错位。

另有一条与环境相关的坑：本地探活须绕开系统 HTTP 代理。企业代理会把
`http://127.0.0.1:...` 也拦成 **502**，Python 侧用 `urllib.request.ProxyHandler({})`
构建 opener 才能拿到真实状态。

LM Studio 本机未安装，只做了 GGUF 目录布局（`<models>/<publisher>/<repo>/<file>.gguf`，
硬链接优先）与接入配置生成，**未做真实加载验证**。

### 25.5 SIMD 后端的可验证边界

AVX-512 与 NEON 后端都不是"写完就算"——本机 CPU 与工具链两处硬约束决定了
能验证到哪一步。

**AVX-512**：本机 i7-8750H（Coffee Lake）CPUID 实测 `AVX512F=0 / BW=0 / VL=0`，
不可能执行。已验证：`gcc -mavx512f -mavx512bw -mavx512vl` 编译通过、
objdump 确认 **198 处 `zmm` 寄存器 + 16 处 `vfmadd132ps`**、
不支持时 `load_avx512()` 抛错（避免非法指令）。**未验证执行正确性。**

**NEON**：无 ARM 工具链、无 QEMU（`wsl.exe` 被安全策略拦）。用
`zig cc -target aarch64-linux-gnu` 真交叉编译出 AArch64 ELF64（`e_machine=183`），
capstone 5.0.7 确认生成 4-lane `fmla v3.4s, v2.4s, v4.4s` 及 `fmul`/`fsub`/`fadd`。
**未验证执行正确性**；执行验证放在 CI 的 `ubuntu-24.04-arm` runner。

这一节的结论就是"产物存在且指令正确"，**不是性能结论**。

## 26. P0 关联记忆与层间输入稀释（CPU 原生质量根因）

`CPU_WAY_OUT.md` 判定："不连贯"有两个独立根因——训练预算不足，与元素级状态的
召回容量上限。本节把两条都落到实测：给主状态加一条矩阵值关联记忆支路（召回容量），
并度量层间输入特异性是否随深度被稀释。

### 26.1 关联记忆的按层成本

`AssocMemory` 的成本 ∝ 开启层数。扫 `assoc_every ∈ {关, 4, 3, 2, 1}`
（small 预设 1.42M、$L$=4，`experiments/_assoc_layers.py`，3 轮独立子进程）：

| 配置 | 开启层 | 参数 | 训练 ms | 倍率 | µs/token | 解码 ms | 倍率 |
|---|---|---|---|---|---|---|---|
| 关闭 | 0 | 1,414,420 | 225.4 | 1.00× | 110.1 | 3.99 | 1.00× |
| 每 4 层 | 1 | 1,445,396 | 284.0 | 1.26× | 138.7 | 3.68 | 0.92× |
| 每 2 层 | 2 | 1,476,372 | 329.9 | 1.46× | 161.1 | 4.66 | 1.17× |
| 每层 | 4 | 1,538,324 | 434.9 | 1.93× | 212.4 | 6.16 | 1.54× |

训练开销**约每层 +22%**（线性）；1 层的 `every4` 只 1.26×，且解码不劣化。

### 26.2 召回容量对开启层数非单调

`experiments/_assoc_recall_layers.py`（dim=64、$L$=4、1500 步、MQAR）：

| 键对数 | 关闭 | 每 4 层 | 每 2 层 | 每层 |
|---|---|---|---|---|
| 2 | 0.984 | 0.977 | **0.988** | 0.977 |
| 4 | 0.121 | 0.441 | **0.656** | 0.164 |
| 8 | 0.047 | 0.070 | 0.027 | 0.074 |

4 对键上**每 2 层（0.656）远优于每层（0.164）**，即全开又慢又差。
⇒ 当前最优形态是**半量开启**。（1500 步未收敛，读作样本效率。）

### 26.3 层间输入稀释：浅模型无、深模型有

**先纠正一条过强结论。** 原判据"不同输入在末层状态的成对余弦 0.50 = 坍缩"是**度量伪影**：
它没有排除跨输入共享的公共分量。补测去均值余弦后（`experiments/_state_collapse.py`，
small、1200 步），逐层**状态**成对余弦 `layer_pair_cos_centered` = **[−0.053, −0.047, −0.060, −0.061]**
（≈0，与随机初始化同量级）；两个输入的状态相对差 0.96–1.07。

`experiments/_branch_breakdown.py` 把块输出 `out = W_c(y) + b_gain·sn + sfb + x` 逐支分解，
每支的**去均值余弦 −0.03~−0.01**、原始余弦 0.54–0.90 ⇒ 原始余弦的相似**全部来自公共分量**，
不是输入特异性丢失。4 层模型上输入特异能量占比随深度反而**上升**（0.285→0.295→0.430→0.597）
——**浅模型没有压缩**。

**深模型确有稀释。** 用 100M 预设收敛态（`experiments/ckpts_100m/sunnynet_p100mw.pt`，
$L$=8、$d$=1408）逐层测：

| 层 | 公共分量 RMS | 输入特异 RMS | 特异能量占比 |
|---|---|---|---|
| 0 | 2.169 | 1.000 | 0.226 |
| 4 | 2.674 | 0.840 | 0.110 |
| 7 | **3.073** | **0.532** | **0.035** |

公共分量**单调增长 +42%**、特异分量**降 47%**，能量占比 0.226→0.035（比值恶化 6.5×）。
输出侧同 ckpt：16 输入只给 **6 个不同 argmax**、成对 JS 散度 0.237（同口径 4 层模型 0.40+）。
**这是"深模型比浅模型更不连贯"的机制。**

在深瘦模型（`deepl8`：$L$=8、$d$=80、0.53M 栈参数）上做因果对照：

| 2000 步 | val ppl | 特异占比 层0→层7 | 稀释降幅 | 24 输入 argmax |
|---|---|---|---|---|
| 默认 | 263.47 | 0.662→0.263 | 0.399 | 19 |
| **残差流归一 `h_norm`** | **625.16** | 0.005→**0.000** | 0.005 | **1** |
| 状态归一 `state_norm` | **259.09** | 0.602→0.302 | 0.299 | 19 |

| 6000 步 | val ppl | 特异占比 层0→层7 | 稀释降幅 | 24 输入 argmax |
|---|---|---|---|---|
| 默认 | 200.51 | 0.460→0.225 | 0.235 | **12** |
| 状态归一 `state_norm` | **198.33** | 0.503→0.267 | 0.236 | **16** |

- **残差流不可清洗**：`h_norm` 把残差流逐 token 归一化，特异分量被压到 0，24 个输入只剩
  1 个预测、ppl 翻倍 ⇒ 证伪。Transformer 的归一化在子层输入而非残差流本身，
  SunnyNet 的 `norm_in` 已对应；改动残差流会破坏 §5 的恒等直连。
- **状态归一是对症方向但只部分缓解**：`state_norm` 归一化状态与反馈源，堵住 DC 从
  `sfb`/`sn` 注入残差流的路径。2000 步把稀释降幅 0.399→0.299、6000 步公共分量增速
  +72%→+54%，输出多样性 **16 vs 12**、ppl **198.33 vs 200.51**（−1.1%），是安全的正向改动。
- **稀释随训练加固**：默认模型 2000→6000 步，ppl 改善（263→201）但 argmax 多样性
  反而从 19 降到 **12**，公共分量 RMS 0.198→0.341（+72%）而特异分量几乎不变（0.183→0.184）
  —— 是**纯稀释**（公共分量膨胀），不是擦除。这解释了"深模型训练越久越不连贯"。
- 末层仍未解（特异占比 0.267 vs 0.225）⇒ 稀释还有状态之外的来源，完整修复仍未达成。

### 26.4 输出侧：公共分量主导，不能直接判"输出坍缩"

`experiments/_output_collapse.py`（从收敛 checkpoint，32 个互不相同输入）：

| 指标 | base | +关联(每层) | 随机初始化 |
|---|---|---|---|
| 末位 logit 成对余弦 | 0.98 | 0.96 | 0.006 |
| **去均值后余弦** | **−0.03** | **−0.02** | — |
| 公共分量能量占比 | **0.975** | 0.961 | — |
| 32 输入的 argmax 去重数 | 27 | 26 | — |

原始余弦 0.98 **约 97% 来自与输入无关的公共分量**（语言模型常见的 unigram 偏置）；
去均值后余弦≈0，32 输入给出 27 个不同 argmax。**该项不可单独解读为"输出坍缩"**，
必须与同规模对照模型比对。

### 26.5 收敛态同预算对照：SunnyNet vs 关联记忆 vs Transformer

四个模型全部训到 16000 步 × B8 × T256 = **32.8M token**（≈19.5 token/参数，
Chinchilla 量级；zh_ancient 单域），栈参数对齐（≤±1%）、同 seed、同 lr 调度。
评测用 `train/evaluate.py`。

| 模型 | 栈参数 | zh_ancient ppl | en ppl | near 召回(1-gram) | 生成 |
|---|---|---|---|---|---|
| SunnyNet 基线 | 365,844 | 143.24 | 8798.69 | 0.023 | 句式可辨、语义漂移 |
| +关联(每层) | 489,748 | 133.36 | 10922.02 | 0.019 | 不连贯 |
| +关联(每 2 层) | 427,796 | 138.82 | 8008.08 | 0.019 | **古文句式连贯** |
| Transformer | 369,200 | 140.40 | 71778.23 | 0.023 | — |

**读数（口径纪律）**：

- **SunnyNet 基线 vs Transformer 同预算同栈参数：ppl 143.24 vs 140.40**（差 2.0%），
  near 召回均 0.023。两者**统计接近**，不是一方压倒。
- **Transformer 在同预算下同样做不到长距召回**（near 0.023 = SunnyNet 基线）。
  ⇒ "不连贯"**主要是 32.8M token 的规模/预算问题，不是 SunnyNet 独有**。
- **关联记忆（每 2 层）把 zh ppl 从 143.24 降到 138.82**（−3.1%），
  栈参数仅 +17%，是唯一改善生成连贯度的配置。
- **输出侧诊断（`_output_collapse.py`）**：

  | 指标 | SunnyNet 基线 | +关联(每层) | +关联(每 2 层) | Transformer |
  |---|---|---|---|---|
  | 末位 logit 余弦 | 0.98 | 0.96 | 0.94 | 0.973 |
  | **去均值后余弦** | **−0.03** | **−0.02** | **−0.03** | **−0.031** |
  | 公共分量占比 | 0.975 | 0.961 | 0.954 | 0.967 |

  Transformer 的去均值余弦（−0.031）与公共分量占比（0.967）与 SunnyNet（−0.03 / 0.975）
  **完全同量级** ⇒ 该现象是**所有架构在低预算下的共性**（unigram 偏置主导下一个巨大
  公共 logit 分量），**不是 SunnyNet 架构缺陷**。此前把原始余弦 0.98 读作"输出坍缩"
  是过强解读，已纠正。

## 28. 层数扩展的代价机制与"扩展断崖"的规避

### 28.1 断崖是什么

一个指标悬在报告 TL;DR：**同参数预算下把层数对齐到 `L=6`，训练步比 `L=4` 慢 30–40%**
（§16.5）。若"层数一多就慢"，向更大规模（更多层）扩展会遇到性能断崖，这直接关系
SunnyNet 能否作为通用大模型骨架。本节把这条从"现象"落到"机制与修复"。

### 28.2 代价律：训练步随层数线性，斜率是一笔固定税

`experiments/_layer_scaling.py --mode affine`（固定 `d=128 / i=192 / r=64`，扫
`L ∈ {1,2,3,4,6,8,10,12}`，T=256、B=8、6 线程，每格独立子进程、3 轮交错取中位）：

| L | 1 | 2 | 3 | 4 | 6 | 8 | 10 | 12 |
|---|---|---|---|---|---|---|---|---|
| ms/step | 121.4 | 158.9 | 195.6 | 267.8 | 310.2 | 365.8 | 414.2 | 499.5 |
| ms/token | 0.0593 | 0.0776 | 0.0955 | 0.1308 | 0.1515 | 0.1786 | 0.2022 | 0.2439 |

最小二乘：**`step_ms ≈ 32.9·L + 102.4`**（每层边际 33 ms、与层数无关的截距 102 ms）。
⇒ 深度代价是**线性且斜率恒定**，不是"某层之后爆炸"。

![规模与深度](../figures/perf_scaling.png)

左图是栈参数 vs 验证 ppl（1.4M / 20M / 100M）：**非单调**，20M 最差、100M 回升，
但三档步数不同（600 / 300 / 100），只读趋势、禁跨档相减。右图即上式代价律的拟合。

### 28.3 斜率来自每层固定的算子派发，不是 FLOPs

同一剖面统计每层新增的 aten 调用数（L=2/4/6/8）：

| 路径 | L=2 | L=4 | L=6 | L=8 | 每层斜率 |
|---|---|---|---|---|---|
| eager torch | 2326 | 4524 | 6722 | 8820 | **+1099** |
| AVX2 融合内核 | 1558 | 2988 | 4418 | 5848 | **+715** |

逐算子分组（L=4）：**`mm` 仅占 1.9%（84 次），`elementwise_other` 占 95.7%（4329 次）**，
其中单层约 1082 次逐元素/视图算子（`as_strided` 535、`mul` 232、`slice` 192、`narrow` 180、
`view` 139、`transpose` 121…）。**每层的 `mm` 只有 21 次**。

⇒ **每层是一笔固定的"算子派发税"（~1100 次调用），与宽度、FLOPs 基本无关。**
融合内核把它从 1099 降到 715（−35%），是唯一已落地的削减手段。
"层数多 = 每层算子集合 × 更多次"，与 §13.3/§14.2/§16.5 的根因判断一致。

### 28.4 每层税分段归因：分散在 5 段，无单一赢家

`experiments/_layer_tax.py` 用替换实验（把某段耗时归零、数值不等价，只测**收益上限**）
给出"该段归零后的每层边际成本"相对基线（基线每层 37.9 ms）：

| 归零段 | 归零后每层 ms | 相对基线 | 说明 |
|---|---|---|---|
| `scan` | 24.8 | **0.654** | 扫描（logspace_scan） |
| `readout` | 25.0 | 0.660 | `W_z`+softwedge+`norm_mix` |
| `compete` | 26.7 | 0.704 | 竞争门控+门控概率 |
| `local` | 26.8 | 0.708 | 深度可分离卷积 |
| `emit` | 28.0 | 0.739 | `W_c/W_s/b_gain/sn` 组装 |
| `norm` | 34.6 | 0.912 | `norm_in` |

⇒ **税高度分散**：单段全融合只削 0.65–0.74 倍，没有一段能独占；把全部段都融合
（不可达的上界）每层也只到约 24.8 ms。**"再写一个融合 kernel"不足以抹平断崖。**

### 28.5 同参数预算下：深度在速度与质量两条轴上都更差

"30–40%" 是在**同参数预算**下测得。`experiments/_scaling_fix.py` 在预算
**365,844（= `small` 栈参数量）**下枚举 6 个 (L, dim) 族，900 步、B8×T256、
2 种子（1234 / 2024）取中位：

| 族 | L | dim | inner | rank | ms/token | zh ppl |
|---|---|---|---|---|---|---|
| **L3 wide** | 3 | 136 | 233 | 97 | **0.0995** | 268.92 |
| **L4 wide** | 4 | 121 | 198 | 77 | 0.1130 | **247.17** |
| L8 narrow | 8 | 67 | 106 | 133 | 0.1132 | 313.94 |
| L4 base | 4 | 128 | 192 | 64 | 0.1184 | 287.84 |
| L6 wide | 6 | 96 | 170 | 64 | 0.1338 | 318.51 |
| L6 narrow | 6 | 92 | 145 | 92 | **0.1346** | 312.62 |

**读数**：

- **速度**：最浅的 `L3 wide` 最快（0.0995），`L6` 两族最慢（≈0.1346），
  **跨度 1.35×**，方向与代价律一致。`L8 narrow`（d67）反而快于 `L6`——因为每层更窄，
  单层税更小；驱动量是 `L × 宽度`，不是裸 `L`。
- **质量**：**深度不买质量**。`L4 wide`（d121）ppl **247.17** 是全场最好；
  `L6`/`L8` 三族全部落在 313–319，比 `L4 wide` 差 27–29%。种子内-间波动约 ±34 ppl
  （`L4 wide` 两种子 264.5 / 229.9），而 `L6/L8` 与 `L4 wide` 的差 ~60 大于波动
  ⇒ 方向可信、幅度需更多种子收紧。
- **口径**：900 步未收敛，单机单实现；本节用于**族间相对比较**，不作绝对质量结论。

⇒ **所谓的"扩展断崖"不是架构在某个层数后失效，而是低秩 + 窄 `dim` 的设计在
参数对齐时被迫堆深、每层交一笔固定派发税，同时深度并不补偿质量。** 这既是性能问题，
也是质量问题的同一个根。

### 28.6 修复：配置纪律优先，而非继续融合

把机制合起来，可落地的修复按优先级：

| # | 手段 | 依据 | 状态 |
|---|---|---|---|
| 1 | **同预算优先浅而宽**：把参数量放进 `inner/rank`，层数封顶在甜点区（实测 4 层） | §28.5 两条轴同时更优；§14.3 在 20M 同向（L10→L6 提速 12.1%、ppl −10.9%） | **采纳（配置纪律）** |
| 2 | 提`rank/dim` 比、加宽 `inner`，减少"靠堆层凑参数"的诱因 | §14.2 层数超同行 +3~+8 层的成因是低秩 + 窄 dim | **采纳（预设改配）** |
| 3 | 融合内核（已落地） | 每层算子 1099→715（§28.3） | 已落地 |
| 4 | 继续融合 `emit/readout/norm` | §28.4 每段仅 0.66–0.74 倍、上界有限 | P2（边际递减） |

**新预设 `p100msw`**（`dim=1536/inner=2624/rank=1152/L=6`，栈参数 **94,470,942**，
对齐 `p100mw` 的 93,828,904 差 **+0.68%**）：把 100M 的层数从 8 压到 6、宽度提 9%。
隔离 A/B（`_scaling_fix.run_cell`，B4×T256、3 轮交错，每格独立子进程）：

| 预设 | L | dim | 栈参数 | ms/token | 相对 |
|---|---|---|---|---|---|
| `p100mw` | 8 | 1408 | 93,828,904 | 4.4111 | — |
| **`p100msw`** | 6 | 1536 | 94,470,942 | **4.2247** | **快 4.2%（3/3 轮占优）** |

⇒ **减层加宽实测省 4.2%，不是纸上估算的 6–8%**（预计未兑现的部分被"增宽 9% 抵消"）。
方向确定、幅度有限：这一档层数下每层税约 33 ms，但加宽也拉长了每层的 matmul。
**深度不再超同行档，且速度、质量（§28.5）同向改善。**

**诚实边界**：本节把断崖从"架构缺陷"改写为"可配置规避的代价律"，但**没有消除**每层
的派发税本身。要真正让"更多层"不掉速，需把每层的逐元素算子大幅并入内核——§28.4 已给出
这条路的收益上界（每层 37.9→24.8 ms 的上限），且 §22.5 已证推理态因张量小无收益。
**在 AVX2-only 的 2018 移动 CPU 上，这一上限就是硬约束。**
